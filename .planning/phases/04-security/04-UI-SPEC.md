# Phase 4 — UI Design Contract

> Visual and interaction contract for per-device security status, on-demand port scans, the alerts feed/banner, and unknown-device/malicious-traffic alert surfacing. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Phase 4 scope (per `04-CONTEXT.md` and `ROADMAP.md` SEC-01..04): (1) a "Scan" action per device that triggers an on-demand port scan and surfaces results, (2) a prominent good/warning/critical security badge on every device card, (3) a dashboard-level alerts feed/banner (unacknowledged `security_alerts`, dismissible) above the device grid alongside the existing Phase 2 summary banner, (4) detection-only surfacing for malicious-IP/suspicious-traffic and unknown-device-joined events — push delivery is explicitly Phase 5's concern. Builds on Phase 1/2/3's dark theme, spacing/typography scale, and component inventory — does not redefine them. This phase introduces the project's **first new semantic color** (a "good/secure" green, since no existing token represents a passing security state) and its **first alert/notification-style UI surface**.

**New shadcn-svelte components required this phase (official registry only):**
- `tooltip` — for the scan-button's disabled/cooldown state and for surfacing the exact flagged port list on hover/focus of the security badge, without needing a full dialog open.
- `alert-dialog` — for the destructive-feeling "Acknowledge alert" / dismiss-all action on the alerts banner (D-12). Acknowledging is not data-destructive (alerts remain in the DB per D-11, just marked acknowledged), but per this project's established pattern (Phase 2/3 only used `dialog` for non-destructive forms), a lighter-weight confirm-on-dismiss is appropriate for "dismiss all" specifically — see Copywriting Contract.
- `alert` — for the dashboard alerts banner itself (a persistent, dismissible list of unacknowledged `security_alerts`), distinct from the existing Phase 2 "device summary" banner pattern (that one is informational counts, not actionable alerts).

No new charting, no new icon library, no new font. Both new components are official shadcn-svelte registry blocks — see Registry Safety.

## Typography

Inherited from Phase 1/2/3, unchanged — no new sizes or weights. Phase 4 maps onto the existing 4 roles:

| Role | Size | Weight | Line Height | Usage in this phase |
|------|------|--------|-------------|----------------------|
| Body | 14px | 400 (regular) | 1.5 | Scan-result port list rows, alert message text, last-scanned timestamp, empty/error state body copy |
| Label | 14px | 500 (medium) | 1.4 | Security badge text ("Good"/"Warning"/"Critical"), "Scan" button label, alert-type labels ("Unknown device", "Malicious IP", "Unexpected port"), scan-result column headers (Port / Service / Status) |
| Heading | 20px | 600 (semibold) | 1.2 | Section titles: "Security Alerts" (banner heading), scan-result dialog/panel title (e.g. "Scan Results — Living Room TV") |
| Display | 28px | 700 (bold) | 1.15 | Unchanged — page-level heading only, not used within this phase's new surfaces |

Weights used: 400, 500, 600, 700 (no new weights; Fontsource load list unchanged — this 4-weight system is the project-wide inherited convention, carried forward unchanged since Phase 1).

**New copy convention (not a new typographic role — a formatting rule):** port numbers are always rendered with their common service name when known (e.g. `23 (Telnet)`, `445 (SMB)`), at Label weight for the port+service pairing and Body weight for any secondary detail — never a bare port number with no context, since the entire point of the scan-result surface is letting a non-expert user understand *why* a port is flagged.

## Color

Inherited from Phase 1/2/3's palette. **One new semantic color is introduced this phase**, justified below — no existing token represents a passing/safe security state without overloading its meaning.

| Role | CSS Variable | Hex | Usage in this phase |
|------|-------------|-----|----------------------|
| Dominant (60%) | `--color-background` | `#0f172a` | Page background (unchanged) |
| Secondary (30%) | `--color-surface` | `#1e293b` | Device cards, alerts banner container, scan-result panel (unchanged) |
| Surface border | `--color-border` | `#334155` | Card outlines, alert-row dividers (unchanged) |
| Accent (10%) | `--color-accent` | `#10b981` | Reserved-for list below — **unchanged scope**, not expanded to cover "good" security status (see rationale) |
| Foreground | `--color-fg` | `#f1f5f9` | Primary text (unchanged) |
| Muted | `--color-muted` | `#64748b` | Secondary text, last-scanned timestamp, inactive/disabled scan button (unchanged) |
| Destructive | `--color-destructive` | `#ef4444` | **Critical** security badge (risky open port or malicious-IP match per D-06), "Malicious IP" / "unexpected risky port" alert rows |
| Warning (existing, from Phase 2) | `--color-warning` | `#f59e0b` | **Warning** security badge (unexpected-but-not-risky port or bandwidth anomaly per D-06), "unexpected port" / "suspicious traffic" alert rows |
| **Good (NEW this phase)** | `--color-good` | `#22c55e` (green-500) | **Good** security badge only — see rationale and reserved-for list below |

**Why a new `--color-good` token is needed (not reusing `--color-accent`):** `--color-accent` (`#10b981`, emerald-500) is already semantically overloaded in this codebase to mean "online / live / active" (the online-status dot on `DeviceCard.svelte`, the SSE "Live" pulse indicator from Phase 3). Reusing it for "security: good" would conflate two unrelated meanings — a device can be online AND have a critical security status simultaneously, and a single green dot already exists on every card for the online state. A visually distinct green (`#22c55e`, green-500 — close enough to read as "the safe color" but distinguishable in a side-by-side from `--color-accent`'s teal-green) avoids this collision. This keeps the 60/30/10 split intact: `--color-good` is a fourth *semantic* status color alongside warning/destructive, not a dominant/secondary/accent role — same treatment as `--color-warning` already received in Phase 2.

**Accent (`#10b981`) remains reserved exclusively for** (unchanged from Phase 1/2/3, not touched by this phase):
- The online/offline status dot on device cards
- The SSE "Live" pulse indicator (Phase 3)
- Active-tab indicators (Phase 3)

**Color contrast check (new pairing):** `--color-good` (`#22c55e`) on `--color-surface` (`#1e293b`) ≈ 5.6:1 — passes WCAG AA for both text and non-text use. `--color-good` text on `--color-background` (`#0f172a`) ≈ 6.5:1 — passes. Both checked against the existing verified-pairing method used in Phase 2/3 UI-SPECs.

**Status-to-color mapping is exhaustive and exclusive (D-06):**
| Status | Color | Never used for |
|--------|-------|-----------------|
| good | `--color-good` | Anything other than the security badge — not used for "online", not used decoratively |
| warning | `--color-warning` | Reused from Phase 2's "unknown device" badge color — same visual language, different meaning context (badge label text disambiguates) |
| critical | `--color-destructive` | Reused from existing error-state color — same visual language as Phase 1/2/3 error states |

## Copywriting Contract

| Element | Copy | Condition |
|---|---|---|
| Security badge — good | `Good` | Device has no flagged ports and no malicious-IP/anomaly signal (D-06); also the default for a never-scanned device |
| Security badge — warning | `Warning` | Device has an unexpected-but-not-risky open port, or a bandwidth-anomaly signal fired (D-06) |
| Security badge — critical | `Critical` | Device has an open risky port, or has communicated with a known-malicious IP (D-06) |
| Scan button (not yet scanned) | `Scan` | Device has never been scanned |
| Scan button (re-scan) | `Re-scan` | Device has a prior scan result |
| Scan button (in progress) | `Scanning…` (disabled state) | Scan request sent, result not yet returned |
| Last-scanned timestamp | `Last scanned {relative time}` (e.g. `Last scanned 2 hours ago`) | Device has at least one prior scan result |
| Never-scanned indicator | `Not yet scanned` | Device has zero scan history — shown near the badge, never as the badge color itself (D-06 explicitly: badge stays "Good" colored, this label is the separate "not yet scanned" surface) |
| Scan result panel heading | `Scan Results — {device name}` | Always, when viewing a completed scan |
| Scan result — open port row label | `{port} ({service name})` e.g. `23 (Telnet)` | Per open port found |
| Scan result — risky port flag | `Risky — commonly exploited` | Port is in the universal risky-ports set (D-05) |
| Scan result — unexpected port flag | `Unexpected for this device type` | Port is open but not in the device type's allowlist and not risky (D-05) |
| Scan result — expected port (informational) | `Expected` | Port is in the device type's allowlist — shown plainly, no warning styling |
| Alerts banner heading | `Security Alerts` | Always, when at least one unacknowledged alert exists |
| Alerts banner — no unacknowledged alerts | Banner is hidden entirely (no "all clear" empty-state banner — an empty alerts list means no banner renders, per the established Phase 2/3 pattern of not showing empty containers where omission is clearer) | Zero unacknowledged `security_alerts` rows |
| Alert row — unknown device | `Unknown device joined the network` | `type: unknown_device` |
| Alert row — malicious IP | `{device name} contacted a known-malicious address` | `type: malicious_ip` |
| Alert row — suspicious traffic | `{device name} shows unusual traffic activity` | `type: suspicious_traffic` |
| Alert row — unexpected port | `{device name} has an unexpected open port` | `type: unexpected_port` |
| Alert row dismiss (single) | `Dismiss` (icon-only × with `aria-label="Dismiss alert"`) | Per-row dismiss/acknowledge action |
| Alert banner — dismiss all | `Dismiss all` | Bulk-acknowledge action; confirmation required (see Destructive Actions below) |
| Empty state — scan in progress, taking a while | Heading: `Still scanning…` / Body: `Port scans can take up to a minute. This will update automatically when it's done.` | Scan request sent more than ~10s ago, no result yet |
| Empty state — scan never run | Heading: `Not yet scanned` / Body: `Run a scan to check this device for open ports and security issues.` | Device has zero scan history, user opens the scan-result detail view |
| Error state — scan failed | Heading: `Scan couldn't complete` / Body: `The device may be offline or unreachable. Try again, or check the capture service logs if this keeps happening.` | Scan request returns an error or times out |
| Error state — alerts feed fails to load | Heading: `Couldn't load security alerts` / Body: `Something went wrong loading alerts. Try refreshing the page.` | API request for `security_alerts` returns non-2xx |
| Destructive-adjacent action — dismiss all alerts | Confirmation dialog title: `Dismiss all alerts?` / Body: `This marks all {N} current alerts as acknowledged. You can still find them in the activity log later.` / Confirm button: `Dismiss all` / Cancel button: `Cancel` | User clicks "Dismiss all" — acknowledging is non-data-destructive (D-11: alerts remain in the table, just flagged `acknowledged`) but bulk-affects multiple records, so a lightweight confirm step is warranted per this project's general caution pattern around bulk/irreversible-feeling actions |

All copy here is plain, factual, and avoids exclamation/marketing tone, consistent with Phase 1/2/3's established voice — security copy in particular avoids alarmist language ("Critical" not "DANGER!", "Risky — commonly exploited" not "HACKERS CAN GET IN").

## Layout

**Primary visual anchor:** the alerts banner (when present) is the topmost, most time-sensitive element on the dashboard — above even the existing Phase 2 summary banner's position would be wrong (summary banner is more "ambient status," alerts are "needs attention now"), so the stacking order is: (1) alerts banner (if any unacknowledged alerts exist), (2) existing summary banner, (3) device grid. Within each device card, the security badge sits in the header row, immediately readable without opening anything — consistent with this project's "at a glance" card philosophy established in Phase 1/2.

## Interaction States

| Element | Default | On interaction |
|---|---|---|
| Security badge | Colored per status (`Good`/`Warning`/`Critical`), static — not clickable itself | Optionally wrapped in `Tooltip` (desktop hover / touch tap) showing a one-line summary of why (e.g. "Port 23 (Telnet) open" or "Contacted a known-malicious address") — opening full detail still requires the Scan button/dialog; the tooltip is a preview, not the primary detail path |
| Scan button | `Scan` (never scanned) or `Re-scan` (has prior result) | On click: button becomes `Scanning…` and disabled; on success, result panel may auto-open or a toast/inline confirmation appears (executor's discretion on exact micro-interaction — contract only requires the new result becomes visible without requiring a manual page refresh); on failure, button returns to its prior label and an inline error message appears near the button (per Error state copy) |
| Scan result panel (`Dialog`) | Closed by default | Opens on demand (clicking a "view results" affordance or after a scan completes); standard `Dialog` keyboard/focus trap behavior, identical to the existing Register/Merge dialogs |
| Alert row dismiss (×) | Visible per row | Clicking immediately marks that single alert acknowledged and removes it from the list (no confirmation needed for single-row dismiss — only the bulk "Dismiss all" requires confirmation, since a single dismiss is low-cost/reversible-feeling and a confirmation on every row would be friction without proportional safety value) |
| Alerts banner "Dismiss all" | Visible when 2+ alerts exist (a single alert can just be dismissed individually — "dismiss all" only adds value at 2+) | Opens the `AlertDialog` confirmation per Copywriting Contract; confirming acknowledges all currently-listed alerts and the banner disappears (or shows newly-arrived alerts if any arrived since the page loaded) |
| Tooltip (scan button / badge) | Hidden | Shows on hover (desktop) or focus/long-press (touch), standard Bits UI `Tooltip` default timing/dismissal — no custom wiring required |

## Accessibility Contract

Inherits Phase 1/2/3's accessibility contract unchanged, plus:

- **Security status is never color-only.** Every badge carries the text label (`Good`/`Warning`/`Critical`) alongside its color — consistent with the existing `--color-warning` "Unknown" badge precedent from Phase 2, which already pairs color with a text label rather than relying on color alone.
- **Alert type icons are decorative, not the sole identifier.** Each alert row's icon (`@lucide/svelte`, color-matched to severity) is `aria-hidden="true"`; the message text itself fully describes the alert type and target device — no information is conveyed by icon/color alone.
- **New `--color-good` passes contrast** at both text and non-text use against `--color-surface` and `--color-background` (see Color section contrast check) — no new untested pairing ships without verification.
- **Dismiss/acknowledge controls are keyboard-operable** with clear `aria-label`s (`Dismiss alert`, `Dismiss all alerts`) — per-row × buttons follow the same `aria-label` pattern already used by the Phase 2.1 info-popover trigger.
- **`AlertDialog` confirmation step** uses Bits UI's default focus trap and `role="alertdialog"` semantics — no custom ARIA wiring required, consistent with this project's reliance on Bits UI primitive defaults (Phase 2's Dialog, Phase 2.1's Popover, Phase 3's Tabs).
- **Touch targets:** Scan button, per-row dismiss (×), and "Dismiss all" all meet the existing 44×44px minimum hit-area exception established in Phase 2.
- **Scan-in-progress state is announced politely.** The `Scanning…` button-label change and any inline error message should be inside a `aria-live="polite"` region (same pattern Phase 3 established for the live-feed connection-state announcements) so screen reader users learn the scan completed/failed without needing to re-poll the button.
