<objective>

Purpose: Prove MOD-06/MOD-07's swappable-support-interface promise on the single most load-bearing piece of existing functionality, using the schema-portability verdict from Plan 01's spike to inform the migration's test strategy.
Output: `backend/src/modules/device_identity/` (support module) and `backend/src/modules/devices/` (feature module) packages, `device_identity` Postgres schema via a new Alembic branch, `main.py` booting via `ModuleLoader`, zero regressions in `test_devices.py` and the capture-ingest test suite.

SET SCHEMA` migration. A signature, return-type, or commit-timing change here breaks device discovery silently (Pitfall 3) since the capture container has no visible error surface on the dashboard.

**Isolated-bisection sequencing (within this single plan, not split into separate plans):**
1. Task 1 (DeviceIdentity extraction) MUST be committed and its full acceptance criteria green — including the full backend suite, not just `test_devices.py` — BEFORE starting Task 2 (Devices retrofit + main.py wiring). This gives a clean git bisect point: if Task 2's work introduces a regression, `git log` shows a Task-1-only commit that already passed full-suite verification, isolating the search to Task 2's diff only.
2. Run `pytest backend/tests/test_devices.py -x` immediately after Task 1 (before Task 2 touches `routes/devices.py`) to confirm DeviceIdentity's extraction alone introduced zero behavior change at the API layer Task 2 will later retrofit.
3. Do not proceed to Task 2 if Task 1's full-suite run shows any regression — fix forward within Task 1's scope first.

If, during execution, Task 1 or Task 2 turns out to need more than ~35-40% of a single context window to complete cleanly, stop and report back rather than rushing the remaining acceptance criteria — this plan's per-task action blocks are intentionally dense (schema migration + model relocation + FK re-pointing + EventBus wiring in Task 1; routes retrofit + manifest + main.py rewiring in Task 2) and accuracy here matters more than completing in one pass.
</risk_summary>
