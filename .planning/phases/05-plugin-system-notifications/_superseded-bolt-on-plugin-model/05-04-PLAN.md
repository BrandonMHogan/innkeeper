## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser → `/api/plugins/*` | Same session-cookie auth boundary as every existing frontend page; no new client-side auth logic introduced |
| Backend-served plugin page descriptor → DOM rendering | The `/plugins/[slug]` page renders backend-supplied `title`/`config_schema` content — must be treated as data, never executable markup |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-14 | Tampering / XSS | `/plugins/[slug]/+page.svelte` rendering the backend descriptor | mitigate | Zero `{@html}` usage anywhere in this route — all descriptor content (title, config_schema labels/values) renders through standard Svelte template interpolation, which auto-escapes; enforced by an explicit grep-based acceptance criterion |
| T-05-15 | Information Disclosure | `PluginConfigDialog`'s masked-secret display | mitigate | The component never receives or stores the raw saved secret value client-side — only the backend's already-masked `"••••" + last4` string from `getPluginDetail`; a fresh value is only sent (never round-tripped) on explicit "Replace token" + Save |
| T-05-16 | Tampering | Switch toggle / config save with no client-side confirmation | accept | Per UI-SPEC's explicit design decision, disabling/enabling and saving config are non-destructive and reversible; only "Remove saved token" (not built this plan — deferred per UI-SPEC's distinction) would need a confirmation, and that destructive action is out of this plan's scope |
</threat_model>
