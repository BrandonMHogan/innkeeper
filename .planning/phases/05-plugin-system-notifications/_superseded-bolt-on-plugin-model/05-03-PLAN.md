<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Backend process → ntfy.sh / Pushover (external services) | Outbound-only HTTP; no inbound surface is added by this plugin |
| `PluginConfig.secrets_json` (token/user_key) → outbound request | The plaintext-stored secret (per D-01) is read and placed into an outbound `Authorization` header or form field — never logged in full |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-10 | Tampering / SSRF | `send_ntfy`'s `server_url` parameter (self-hosted ntfy support) | mitigate | `server_url` is restricted to `https://` scheme only; any other scheme is rejected before a request is attempted, never silently sent |
| T-05-11 | Information Disclosure | Logging inside `send_ntfy`/`send_pushover`/`handle_new_device` on failure | mitigate | Log statements print the exception/skip-reason only, never the resolved `token`/`user_key` secret value itself |
| T-05-12 | Denial of Service | A hung ntfy.sh/Pushover connection during `handle_new_device` | mitigate | Inherited from Task 1's `httpx.AsyncClient(timeout=10.0)` on every sender call — bounded worst-case latency per notification attempt, and the EventBus's own fire-and-forget dispatch (Plan 05-01) bounds the blast radius further |
| T-05-13 | Tampering | Notification plugin's manifest declaring `required_capabilities: []` | accept | This plugin requests no special capabilities; no capability-enforcement layer exists this phase (out of scope per REQUIREMENTS.md's PDST-02 deferral) — consistent with Plan 05-01's T-05-04 disposition |
</threat_model>
