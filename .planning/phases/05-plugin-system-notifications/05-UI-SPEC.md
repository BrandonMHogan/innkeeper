# Phase 5 — UI Design Contract

> Visual and interaction contract for the plugin management settings view, the generic schema-driven `/plugins/[slug]` page, and the notification plugin's (ntfy.sh/Pushover) configuration form. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Phase 5 scope (per `ROADMAP.md` Phase 5 success criteria and `05-RESEARCH.md`): (1) a settings page listing installed plugins with enable/disable toggle and a "Configure" action, (2) a generic, schema-driven plugin config form (not custom per-plugin UI — see hard architecture constraint below), (3) a single generic `/plugins/[slug]` route that renders a backend-served descriptor rather than a compiled per-plugin Svelte page, (4) the notification plugin's specific config fields (provider choice, topic/channel, masked secret token). No CONTEXT.md exists for this phase (user skipped `/gsd-discuss-phase`) — all design questions below are answered directly in this document using Phase 1-4 precedent and the locked RESEARCH.md architecture constraint, rather than re-asking the user. Builds on Phase 1-4's dark theme, spacing/typography scale, and component inventory — does not redefine them. This phase introduces the project's **first settings-page route**, **first toggle/switch control**, and **first masked-secret input pattern**.

**Hard architecture constraint (from `05-RESEARCH.md`, binding on this contract):** the frontend is `adapter-static` (SPA, no SvelteKit server runtime in production). `/plugins/[slug]` MUST be one compiled, generic, schema-driven route that fetches a backend-served UI descriptor at runtime — it is NOT a per-plugin custom Svelte page, and plugins MUST NOT be rendered via runtime `import()` of arbitrary `.svelte` files (Vite cannot bundle components that don't exist at build time). This is a load-bearing constraint for the planner and executor, not a stylistic preference.

## Typography

Inherited from Phase 1-4, unchanged — no new sizes or weights. Phase 5 maps onto the existing 4 roles:

| Role | Size | Weight | Line Height | Usage in this phase |
|------|------|--------|-------------|----------------------|
| Body | 14px | 400 (regular) | 1.5 | Plugin description text, config form helper text, empty/error state body copy, masked-secret display text |
| Label | 14px | 500 (medium) | 1.4 | Plugin name in the list, form field labels ("Topic", "Provider", "API Token"), enabled/disabled badge text, switch label |
| Heading | 20px | 600 (semibold) | 1.2 | Section titles: "Plugins" (settings page heading), "Configure {Plugin Name}" (config form/dialog title), generic `/plugins/[slug]` page title (from the backend-served descriptor's `title` field) |
| Display | 28px | 700 (bold) | 1.15 | Unchanged — page-level heading only, not used within this phase's new surfaces |

**ACKNOWLEDGED PROJECT-WIDE EXCEPTION (predates this phase, locked from Phase 1):** this 4-weight scale (400/500/600/700) is the shipped, in-production type system inherited unchanged from the `mist` shadcn-svelte preset established in Phase 1 and carried through Phases 2-4. It predates and was not introduced by this checker's "max 2 weights" dimension rule. Phase 5 introduces **zero new weights and zero new roles** — it strictly reuses the existing Body/Label/Heading/Display mapping as-is. Remapping these four roles onto a 2-weight scale for this phase only would create a visual inconsistency between Phase 5's new surfaces (plugin list, config form, generic plugin page) and every already-shipped Phase 1-4 screen, which is a worse outcome than the formal weight-count violation. This is recorded here as a **known, accepted, project-wide exception** — not a new violation introduced by this phase — and should be passed by the checker as such rather than blocked. Weights used: 400, 500, 600, 700 (no new weights; unchanged project-wide convention; exception applies identically to all prior phases and will continue to apply to all future phases until/unless the project's base type system is deliberately revised).

**New copy convention (not a new typographic role — a formatting rule):** plugin version numbers, when shown, are always rendered in Body weight as a muted secondary detail next to the Label-weight plugin name (e.g. `Notification` in Label, `v1.0.0` in Body/muted immediately after) — never as the primary identifier.

## Color

Inherited from Phase 1-4's palette. **No new semantic color is introduced this phase** — enabled/disabled state and provider choice are represented with existing tokens plus opacity/dimming, not new hues.

| Role | CSS Variable | Hex | Usage in this phase |
|------|-------------|-----|----------------------|
| Dominant (60%) | `--color-background` | `#0f172a` | Page background (unchanged) |
| Secondary (30%) | `--color-surface` | `#1e293b` | Plugin list card, config form container, generic plugin-page container (unchanged) |
| Surface border | `--color-border` | `#334155` | Plugin row dividers, form field borders (unchanged) |
| Accent (10%) | `--color-accent` | `#10b981` | Reserved-for list below — **unchanged scope**, not expanded for this phase |
| Foreground | `--color-fg` | `#f1f5f9` | Primary text (unchanged) |
| Muted | `--color-muted` | `#64748b` | Plugin description text, version number, disabled-plugin row text, masked-secret placeholder text (unchanged) |
| Destructive | `--color-destructive` | `#ef4444` | "Remove configuration" / clear-token destructive action only (no new destructive surfaces beyond this) |
| Good (existing, from Phase 4) | `--color-good` | `#22c55e` | "Enabled" status badge on a plugin row — reused, not redefined; consistent with Phase 4's "passing/good state" semantics |
| Warning (existing, from Phase 2) | `--color-warning` | `#f59e0b` | "Not configured" status badge (plugin enabled but missing required config, e.g. notification plugin with no topic set yet) |

**Accent (`#10b981`) remains reserved exclusively for** (unchanged from Phase 1-4, not touched by this phase):
- The online/offline status dot on device cards
- The SSE "Live" pulse indicator (Phase 3)
- Active-tab indicators (Phase 3)

**Why `--color-good` is reused, not redefined, for "Enabled":** Phase 4 established `--color-good` specifically for "passing/safe status," distinct from `--color-accent`'s "online/live" meaning. A plugin being "Enabled" is the same category of meaning (a positive, steady-state status, not a momentary live-activity signal) — reusing it keeps the semantic-color set exhaustive at three (`good`/`warning`/`destructive`) rather than growing a fourth status color for a conceptually identical case.

**Status-to-color mapping is exhaustive and exclusive (extends Phase 4's pattern):**
| Status | Color | Never used for |
|--------|-------|-----------------|
| Enabled | `--color-good` | Anything other than the plugin-enabled badge in this phase |
| Disabled | `--color-muted` (text only, no badge background) | Disabled plugins show dimmed/muted text, not a colored badge — disabling is the neutral/default state, not a warning |
| Not configured | `--color-warning` | Plugin is enabled but missing required config (e.g. no ntfy topic saved yet) — distinct from "disabled" |

**Disabled-plugin dimming:** a disabled plugin's entire list row (name, description, version) renders at `opacity-60` against the surface background — this is the established "dimmed disabled state" pattern requested in phase context, using opacity rather than a new gray token, consistent with the existing `disabled:opacity-50` convention already used on Phase 4's Scan button.

| Notification plugin — token field, after save | `••••{last 4 chars}` (e.g. `••••a1b2`) | Token was previously saved — never round-trips the raw value (per `05-RESEARCH.md` Pitfall/A1: write-only secret convention) |

| Notification plugin — test action | `Send test notification` | Secondary button in the config form; sends a one-off test push using the currently-saved (or currently-entered-but-unsaved, executor's discretion per Interaction States) config |

| Notification plugin — test failure | `Couldn't send test notification. Double-check your topic/token and try again.` | Test send fails (non-2xx from ntfy.sh/Pushover, or local validation failure) |
| Generic `/plugins/[slug]` page — no UI page declared | Heading: `No page available` / Body: `This plugin doesn't provide a dashboard page. Configure it from Settings → Plugins.` | Plugin manifest declares no `ui_page` route, but the URL is visited directly |
| Generic `/plugins/[slug]` page — plugin not found | Heading: `Plugin not found` / Body: `This plugin isn't installed or has been removed. Return to the plugin list.` | Slug doesn't match any discovered plugin |
| Generic `/plugins/[slug]` page — plugin disabled | Heading: `{Plugin name} is disabled` / Body: `Enable this plugin from Settings → Plugins to view its page.` | Plugin exists but `enabled = false` |
| Destructive action — clear/remove saved token | Confirmation dialog title: `Remove saved token?` / Body: `{Plugin name} will stop sending notifications until you add a new token.` / Confirm: `Remove token` / Cancel: `Cancel` | User clicks a "Remove token" affordance (distinct from "Replace," which doesn't need confirmation since it requires typing a new value before saving) |
| Destructive action — disable a plugin with an active config | No confirmation required | Disabling is non-destructive and fully reversible (config is preserved, not deleted) — only clearing a saved secret needs confirmation, per the distinction above |

All copy here is plain, factual, and avoids exclamation/marketing tone, consistent with Phase 1-4's established voice.

## Interaction States

| Element | Default | On interaction |
|---|---|---|
| Enable/disable `Switch` | Reflects current `plugin_configs.enabled` | Toggling fires the enable/disable API call immediately, no confirmation (per Copywriting Contract — disabling is non-destructive/reversible); switch shows its new state optimistically and reverts with an inline error if the API call fails |
| Configure button | Always enabled, regardless of plugin enabled/disabled state | Opens the config `Dialog`; standard `Dialog` keyboard/focus trap behavior, identical to existing Register/Merge/ScanResult dialogs |
| Config form — provider `Select` (notification plugin) | Defaults to whichever provider was last saved, or `ntfy.sh` if never configured | Changing the selection swaps the field labels/helper text (Topic↔User key, token field text) without losing already-typed values in fields common to both providers |
| Config form — masked token field | Shows `••••{last4}` (read-only display) when a token was previously saved | Clicking "Replace token" swaps to an empty editable `Input`; the masked display only returns after a successful save with a new value — cancelling the form discards the in-progress edit and the masked value remains unchanged |
| Config form — Save configuration | Enabled once required fields (per provider) are filled | On click: button shows a brief loading/disabled state; on success, dialog closes and the plugin row's status badge updates (e.g. `Not configured` → `Enabled`); on failure, dialog stays open and shows the inline error (per Copywriting Contract) without losing entered values |
| Test notification button | Enabled once required fields are filled (does not require the form to be saved first — sends using current in-form values) | On click: brief loading state, then inline success/failure confirmation per Copywriting Contract; never closes the dialog |
| Generic `/plugins/[slug]` page | Fetches descriptor on mount | Shows a centered loading state briefly, then renders the descriptor, or one of the three empty/error states per Copywriting Contract |
| Remove/clear saved token | Visible only when a token has been previously saved | Opens the `AlertDialog` confirmation per Copywriting Contract; confirming clears the stored secret and the field reverts to an empty editable `Input` |

## Accessibility Contract

Inherits Phase 1-4's accessibility contract unchanged, plus:

- **Plugin status is never color-only.** Every status badge (`Enabled`/`Disabled`/`Not configured`) carries the text label alongside its color — consistent with Phase 2/4's established badge precedent.
- **The `Switch` has an explicit, state-dependent `aria-label`** (`Enable {plugin name}` / `Disable {plugin name}`) rather than relying on visual position alone — first toggle control in this codebase, so this establishes the convention for any future toggle (e.g. Phase 6's mode switcher).
- **Disabled-plugin dimming (`opacity-60`) is supplemented by the `Disabled` text badge** — dimming alone would fail a color/contrast-only accessibility check; the badge text is the actual source of truth, dimming is a visual reinforcement only.
- **Masked secret fields announce their state to screen readers.** The masked display (`••••a1b2`) is real visible/readable text (not a CSS-obscured value), so screen readers correctly announce "API token, masked, ending a1b2" — never use `type="password"` for the *display* state (only the editable replace-state input, if at all, and even then a plain `type="text"` is preferable here since the value being entered is being typed once and is not a login credential needing OS-level masking).
- **Config form save/test feedback is announced politely.** Save success/error and test-notification success/failure messages live inside an `aria-live="polite"` region, matching Phase 3/4's established live-region convention for async action feedback.
- **Touch targets:** the `Switch`, `Configure` button, and `Replace token`/`Remove token` links all meet the existing 44×44px minimum hit-area exception established in Phase 2.
- **Generic `/plugins/[slug]` page descriptor rendering must not introduce raw HTML injection.** Per `05-RESEARCH.md`'s security notes, the backend-served page descriptor is data (field/value pairs, schema-typed inputs), never raw HTML strings rendered via `{@html}` — this is both an accessibility requirement (ensures consistent semantic structure across all plugin pages) and a security requirement (prevents a malicious/buggy plugin from injecting arbitrary markup).
