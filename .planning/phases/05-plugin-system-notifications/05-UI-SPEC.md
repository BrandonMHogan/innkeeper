# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Phase 5 is primarily backend module-host infrastructure (MOD-01..MOD-07). The frontend scope is narrow and explicit per CONTEXT.md D-18–D-22: (1) **consolidate** the design-token source and shared component library that already exist from Phases 1-4 — formalizing what is implicit today, not inventing a new look — and (2) land that consolidation **before** the Devices/Traffic/Security UI markup is retrofitted onto module routes, plus (3) the net-new "Linked Apps" empty-state section (MOD-08) and a module nav entry pattern (MOD-04). This UI-SPEC is the contract the retrofitted pages and the two new surfaces must follow. No new screens are being designed from scratch.

## Spacing Scale

Declared values (must be multiples of 4) — already in use across Phases 1-4 inline styles, formalized here as the contract:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps, badge internal padding |
| sm | 8px | Compact element spacing (flex gaps between inline controls) |
| md | 16px | Default element spacing (heading-to-content margin, card internal gaps) |
| lg | 24px | Section padding (`<main>` page padding, card padding, banner padding) |
| xl | 32px | Layout gaps between major page regions |
| 2xl | 48px | Major section breaks (e.g. margin below the per-device bandwidth section) |
| 3xl | 64px | Page-level spacing (reserved; not yet used, available for new module pages) |

Exceptions:
- Touch targets (buttons, the device-picker `<select>`) use `min-height: 44px` regardless of the spacing scale — accessibility floor, carried over from Phase 1-4.
- Card grid uses `grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))` with a `24px` (lg) gap — this is the established device-card-grid pattern; the new "Linked Apps" card grid (MOD-08) must reuse this exact pattern, not invent a new one.

## Typography

Formalizing the inline-style values already established in `dashboard/+page.svelte` and component files (Phases 1-4) into a declared scale. New module pages (settings/modules, `/modules/[slug]`, Linked Apps) must use these values — prefer Tailwind utility classes (`text-sm`, `font-semibold`, etc.) over hand-written inline `style=` strings going forward, but the **pixel/weight/line-height values themselves must match this table**.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / label | 14px | 500 (medium) | 1.4 |
| Section label (muted) | 14px | 500 (medium) | 1.4 |
| Card title | 16px | 600 (semibold) | 1.3 |
| Page heading (h1) | 28px | 700 (bold) | 1.15 |

**Declared scale: exactly 3 sizes (14 / 16 / 28), exactly 2 weights (500 / 700) plus one bridging semibold (600) reserved for card/dialog titles only** — this matches what Phases 1-4 already shipped; do not introduce a 4th size or a 5th weight for Phase 5's new surfaces (module settings page, nav entries, Linked Apps cards). Module nav entry labels use the body/label role (14px/500/1.4).

## Color

Dark-only theme — no light mode. Values from `frontend/src/lib/styles/theme.css` `:root`/`.dark`:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0f172a` (`--color-background`) | Page background |
| Secondary (30%) | `#1e293b` (`--color-surface`) | Cards, dialogs, popovers, the device-picker select, banners |
| Accent (10%) | `#10b981` (`--color-accent`) | Reserved for: focus ring (`--ring`), "live"/online indicators (e.g. `SecurityAlertsBanner`'s Radio icon), primary button background (`--color-accent-button-bg` `#059669`, a darker accent shade used only for primary CTA buttons) |
| Destructive | `#ef4444` (`--color-destructive`) | Destructive actions only: critical security badge, "Dismiss all" confirmation, delete/remove affordances |

Additional semantic tokens already established (not part of the 60/30/10 split but locked brand aliases — reuse, do not redefine):
- `--color-warning` `#f59e0b` — warning security badge, unknown-device count, non-destructive caution states
- `--color-good` `#22c55e` — good security badge only (intentionally distinct from `--color-accent`'s teal-green to avoid conflating "secure" with "live/online")
- `--color-muted` `#64748b` — secondary/muted text (timestamps, helper copy)
- `--color-border` `#334155` — all card/dialog/input borders

Accent reserved for: focus rings, live/online status indicators, primary CTA button backgrounds. Never use accent for body text, card backgrounds, or as a generic "interactive element" color — those are `--color-surface` and `--color-fg` with `--color-border` outlines.

**New for Phase 5 — module enable/disable toggle state:** reuse `--color-accent` for "enabled" toggle-on state and `--color-muted` for "disabled" toggle-off state, consistent with the existing semantic-color discipline (never color-only — pair with a text label "Enabled"/"Disabled", not just toggle position, since this is a settings control).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (module settings page) | "Enable module" / "Disable module" (per-row toggle action; button label flips with state, not a single ambiguous "Toggle") |
| Primary CTA (Linked Apps empty state) | No CTA button — v1 ships data model + empty state only (D-23); do not add an "Add linked app" button this phase, that affordance doesn't exist until a real linked module ships in v2 |
| Empty state heading (Linked Apps section, zero entries) | "No linked apps yet" |
| Empty state body (Linked Apps section) | "Linked apps will appear here once a third-party module is configured." (no actionable next step yet — honest about v1 scope per D-23, not a dead-end CTA to a feature that doesn't exist) |
| Empty state heading (Modules settings page, hypothetical zero-modules edge case) | "No modules installed" |
| Error state (module fails to load at startup) | "{module display_name} couldn't start" + "Check the server logs for details" — mirrors the existing `DeviceCard` pattern ("Scan couldn't complete") of naming the failed action plainly, no jargon like "manifest validation failed" |
| Error state (module route disabled, 404) | Not a user-facing copy concern — disabled-module routes simply 404 and the nav entry is hidden; no error banner needed since the UI never offers a path to a disabled module |
| Destructive confirmation (disable a module with dependents) | "Disable {module display_name}?": "{N} other module(s) depend on this and will also stop working. This won't delete any data." — pattern matches existing `SecurityAlertsBanner`'s `AlertDialog` confirmation copy style (action question as title, consequence + reassurance as body) |
| Destructive confirmation (none other this phase) | No other destructive actions are introduced by Phase 5's frontend scope — module disable (above) is the only one; Devices/Traffic/Security retrofit must preserve all existing destructive-action copy unchanged (e.g. "Dismiss all alerts?" from `SecurityAlertsBanner`) |

**Retrofit constraint:** Devices/Traffic/Security pages keep their exact existing copy through the retrofit (Risk Summary's behavior-parity requirement applies to UI text too, not just API responses) — this UI-SPEC formalizes the visual contract those pages must continue to satisfy, it does not change their wording.

## New Surfaces This Phase — Interaction Contract

These two surfaces are net-new (not a retrofit of existing markup) and need explicit interaction notes beyond the token tables above:

### Module nav entry (MOD-04)
- An enabled module with `HasUIPage` appears as a nav-list entry (reuse body/label typography: 14px/500/1.4) linking to `/modules/[module-name]`.
- A disabled module has no nav entry at all — never shown-but-grayed-out, since its route 404s. Don't build a "disabled, can't click" nav state; the entry simply doesn't render when the module is disabled per the architecture's `require_module_enabled` 404 pattern.

### Module settings page (MOD-02)
- One row per module: `display_name`, enable/disable toggle, optional "Configure" affordance (deferred to whichever module actually needs settings — e.g. Phase 5.2's Notifications channel/topic fields — this phase only needs the list + toggle, not a generic settings-form renderer).
- Disabling a module that other enabled modules `require` triggers the destructive-confirmation copy above before committing.

### Linked Apps section (MOD-08)
- Lives on the dashboard (or settings page — Claude's Discretion on exact placement, not locked by CONTEXT.md) as a card-grid section using the exact same `grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))` / 24px gap pattern as the Devices card grid.
- Zero entries today (v1 ships no real linked module) → renders the empty-state heading/body above, not an empty grid with no explanation.
- A linked-app card (when one eventually exists) shows `icon_url`, `name`, and opens `target_url` — out of scope to design the card's internals further this phase since no real entry ships.
