<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser (authenticated session) → `/api/plugins/*` | Same session-cookie trust boundary as every other authenticated route — no new auth mechanism |
| Plugin-registered router (e.g. notification plugin, Plan 05-03) → `/api/plugins/{id}/*` | A plugin's own routes are mounted at startup regardless of enabled state; `require_plugin_enabled` is the actual access-control boundary, not route registration |
| Capture-ingest hot path (`discovery.py`, `capture.py`) → `EventBus.publish` | Untrusted-adjacent ARP/DHCP/mDNS observations ultimately trigger `new_device`/`traffic_spike` publishes — must never let a plugin handler's failure or latency propagate back into this ingest path (already mitigated by Plan 05-01's fire-and-forget EventBus, this plan is the first real caller proving it) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-05 | Elevation of Privilege | A disabled plugin's API routes remain in FastAPI's routing table | mitigate | `require_plugin_enabled(plugin_id)` dependency on every plugin-registered route, checked against `PluginConfig.enabled` on every request — returns 404 (not 403, to avoid confirming the plugin's existence to an unauthenticated-adjacent prober; though `require_auth` already runs first) |
| T-05-06 | Information Disclosure | `GET /api/plugins/{plugin_id}` / config responses | mitigate | `_serialize_plugin_config` masks every `config_schema` field marked `type: "secret"` to `"••••" + last4`; raw `secrets_json` values are never serialized into any response body |
| T-05-07 | Tampering | `POST /api/plugins/{id}/config` accepting arbitrary keys | mitigate | Server-side validation rejects any submitted config key not present in the plugin's manifest `config_schema` (422), preventing a malicious/buggy client from writing arbitrary JSON into `config_json`/`secrets_json` |
| T-05-08 | Denial of Service | `device_lost_detector`'s periodic full-table `Device` scan | accept | Device count for a home-network single-user tool is small (tens, not millions); a 60s full-table scan is negligible load, consistent with `traffic_broadcaster`'s existing 7s full-table-adjacent scan precedent |
| T-05-09 | Denial of Service | A plugin's `event_subscriptions` handler blocking the EventBus | mitigate | Already covered by Plan 05-01's `EventBus.publish` fire-and-forget design; this plan is the first real-world exercise of that guarantee against actual capture-ingest traffic |
</threat_model>
