# Phase 02.1: Device Identification Hints - Context

**Gathered:** 2026-06-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Add best-effort vendor + type inference to unknown (unregistered) device cards on the dashboard, derived from MAC OUI, mDNS service type, and DHCP vendor class — and reuse that same inference to pre-fill (never lock) the Register dialog's name/type fields. No inference for already-registered devices, no confidence scoring UI, no feedback/correction loop, no bulk-accept. Visual/copy treatment is locked by `02.1-UI-SPEC.md`; this discussion covers the inference logic and one new interaction (raw-signal info popover) that UI-SPEC does not yet cover.

</domain>

<decisions>
## Implementation Decisions

### Vendor Name Display
- **D-01:** Vendor display uses a **curated friendly-name shortlist** (e.g. Apple, Samsung, Sonos, Google, Amazon, Roku — exact list is research/planner's discretion, starting from common consumer-electronics brands). A MAC OUI that doesn't match an entry in the curated list shows **no vendor** at all — never the raw/legal OUI registrant string (e.g. never "Hon Hai Precision Industry Co.,Ltd."). User has no specific vendors they need guaranteed; a generic common-consumer starter list is acceptable.
- **D-02:** This means full-database vendor lookup (e.g. `mac-vendor-lookup`) MAY still be used internally as the underlying OUI→registrant lookup, but only entries that map through the curated friendly-name list are ever shown as "vendor" on the card or in the pre-fill. Raw/uncurated OUI strings are never displayed in the normal inference line (see D-07 for where raw data IS shown).

### Type-Guess Signal Policy
- **D-03:** Maintain a short list of **single-category vendors** (vendors that overwhelmingly make one kind of consumer device — e.g. Sonos→smart-home, Roku→TV/streaming, Nest→smart-home). For these, **vendor alone is sufficient** to guess a type, even with no mDNS/DHCP signal.
- **D-04:** For **multi-category vendors** (Apple, Samsung, Google, Microsoft, and similar — vendors that plausibly make phones, laptops, TVs, smart-home devices, etc.), vendor alone is **never** sufficient for a type guess. A type guess for these vendors requires a corroborating mDNS service type or DHCP vendor class signal. Vendor name may still be shown on its own (per D-01) even when type cannot be guessed.
- **D-05:** The single-category vs. multi-category vendor classification is a maintainable list/lookup, not a one-off hardcoded branch — future vendors can be added to either bucket without changing the inference algorithm's shape.

### Conflicting-Signal Resolution
- **D-06:** When vendor-implied type and mDNS/DHCP-implied type disagree, **mDNS/DHCP wins** — protocol-level signals are more direct evidence of device behavior than a vendor-name heuristic. Vendor-implied type is only used as a fallback when no mDNS/DHCP signal exists (or when an mDNS/DHCP signal exists but doesn't map to any known type).

### Raw-Signal Transparency (new interaction — extends UI-SPEC)
- **D-07:** Add a small **"i" info affordance** next to the inference line on unknown device cards. Tapping/clicking toggles a small popover showing the **raw, uncleaned signal data** that fed the guess: MAC address, raw/full OUI vendor string (before D-01's curated cleanup), mDNS service type if observed, DHCP vendor class if observed. Purpose: let the user see why the system guessed what it guessed, especially when the guess looks wrong or is absent.
- **D-08:** Content is **raw signals only** — no narrative explanation of which signal "won" (i.e., no reasoning/justification text, just the facts: MAC / vendor OUI string / mDNS service type / DHCP vendor class, each shown only if present).
- **D-09:** Interaction MUST work identically on desktop and touch (the dashboard is explicitly usable from any device on the network — hover-only is not acceptable). Use a **click/tap-to-toggle popover**, not a hover-only tooltip. If shadcn-svelte's existing Popover/Tooltip primitive already handles open-on-click with click-away-to-dismiss, reuse it as-is rather than building a custom toggle.
- **D-10:** **UI-SPEC.md amendment required:** `02.1-UI-SPEC.md` as currently written says "No new icon-only controls are introduced" and does not define a popover pattern, contrast-checked color, or touch target for an info icon. The planner/researcher MUST either request a UI-SPEC update (re-run `/gsd-ui-phase 02.1`) covering: the info icon's visual treatment, the popover's layout/copy/contrast, and the 44×44px touch target, OR explicitly note this as a UI-SPEC gap to close before/during execution. This decision was captured after UI-SPEC was already approved — it is not yet reflected there.

### Claude's Discretion
- Exact curated vendor shortlist contents (which brands, how many) for D-01/D-03
- Exact single-category vs. multi-category vendor bucket membership for D-03/D-04
- Internal schema changes needed to carry mDNS service_type / DHCP vendor_class_id from the raw event tables into `DiscoveredIdentity` (currently only `mac` + `hostname` are persisted — see Code Insights below) so the inference engine has these signals available at query time
- Exact wording inside the info popover (beyond "raw signals only" per D-08)
- Whether the curated vendor lookup and single/multi-category vendor list live as static data, a config file, or inline code — implementation detail

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `backend/src/services/identity_resolver.py` — `MDNS_PLACEHOLDER_MAC` sentinel already exists and is exactly the "non-placeholder MAC" concept DISC-05 requires for vendor inference (a placeholder-MAC identity must never attempt vendor lookup).
- `backend/src/models/discovered_identity.py` — Current `DiscoveredIdentity` row only stores `mac` + `hostname`. It does **not** currently retain `mdns_events.service_type` or `dhcp_events.vendor_class_id` — those exist in the raw ingest tables (`backend/src/models/mdns_event.py`, `backend/src/models/dhcp_event.py`) but aren't joined/copied into the fused identity row. The inference engine needs access to these signals per-identity; closing this gap (new columns vs. a join/lookup at read time) is planner/researcher's call.
- `backend/src/models/device.py` — `DeviceType` enum (8 fixed values: phone, laptop, desktop, tablet, iot_smart_home, tv_streaming, game_console, router_network, other) is the closed set any type guess MUST map onto.
- `backend/src/routes/devices.py` — `_serialize_identity()` is where a `vendor` / `type_guess` field would naturally be added to the unknown-identity payload consumed by the frontend.
- `frontend/src/lib/components/DeviceCard.svelte` — Unknown-device branch (lines 62-86) is where the new inference line + info popover render, per UI-SPEC's locked layout.
- `frontend/src/lib/components/RegisterDialog.svelte` — `name`/`type` `$state` initial values currently always start `''`/`undefined`; pre-fill means seeding these from the identity's inference payload when the dialog opens for a given `identityId`.

### Established Patterns
- Capture container → POST-to-API → ingest route → DB pattern (Phase 1/2) is unchanged by this phase; no new capture-side work, only backend inference logic over already-ingested `dhcp_events`/`mdns_events` and a frontend rendering/pre-fill change.

### Integration Points
- New inference logic sits between the existing ingest tables (`dhcp_events`, `mdns_events`, `discovered_identities`) and the `/api/devices` response — likely a new service module (analogous in spirit to `identity_resolver.py`) rather than inlined into the route.

</code_context>

<specifics>
## Specific Ideas

- The "i" info popover came from the user wanting a safety valve for when the system's guess is wrong or unclear — "just dumps the info to the user" so they can see the raw evidence rather than trusting an opaque guess. This is explicitly NOT meant to be always-visible clutter — toggle-on-demand only.
- No specific vendors the user needs guaranteed in the curated shortlist — generic common-consumer coverage is fine to start.

</specifics>
