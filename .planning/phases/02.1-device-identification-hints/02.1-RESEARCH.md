### Locked Decisions

**Vendor Name Display**
- **D-01:** Vendor display uses a curated friendly-name shortlist (e.g. Apple, Samsung, Sonos, Google, Amazon, Roku — exact list is research/planner's discretion, starting from common consumer-electronics brands). User has no specific vendors they need guaranteed; a generic common-consumer starter list is acceptable.
- **D-02:** This means full-database vendor lookup (e.g. `mac-vendor-lookup`) MAY still be used internally as the underlying OUI→registrant lookup, but only entries that map through the curated friendly-name list are ever shown as "vendor" on the card or in the pre-fill. Raw/uncurated OUI strings are never displayed in the normal inference line (see D-07 for where raw data IS shown).

**Type-Guess Signal Policy**
- **D-03:** Maintain a short list of single-category vendors (vendors that overwhelmingly make one kind of consumer device — e.g. Sonos→smart-home, Roku→TV/streaming, Nest→smart-home). For these, vendor alone is sufficient to guess a type, even with no mDNS/DHCP signal.
- **D-04:** For multi-category vendors (Apple, Samsung, Google, Microsoft, and similar), vendor alone is never sufficient for a type guess. A type guess for these vendors requires a corroborating mDNS service type or DHCP vendor class signal. Vendor name may still be shown on its own (per D-01) even when type cannot be guessed.
- **D-05:** The single-category vs. multi-category vendor classification is a maintainable list/lookup, not a one-off hardcoded branch — future vendors can be added to either bucket without changing the inference algorithm's shape.

**Conflicting-Signal Resolution**
- **D-06:** When vendor-implied type and mDNS/DHCP-implied type disagree, mDNS/DHCP wins — protocol-level signals are more direct evidence of device behavior than a vendor-name heuristic. Vendor-implied type is only used as a fallback when no mDNS/DHCP signal exists (or when an mDNS/DHCP signal exists but doesn't map to any known type).

- **D-08:** Content is raw signals only — no narrative explanation of which signal "won" — just the facts: MAC / vendor OUI string / mDNS service type / DHCP vendor class, each shown only if present.
- **D-09:** Interaction MUST work identically on desktop and touch — click/tap-to-toggle popover, not a hover-only tooltip. Reuse shadcn-svelte's Popover primitive's open-on-click with click-away-to-dismiss as-is.

## Summary

This phase adds a pure-inference layer on top of Phase 2's already-shipped discovery pipeline — no new capture-side work. The backend needs three things: (1) two new nullable columns (`mdns_service_type`, `dhcp_vendor_class`) on `discovered_identities` populated at upsert time from the already-ingested `mdns_events`/`dhcp_events` rows so the inference engine has them at read time without a join; (2) a new `backend/src/services/identity_inference.py` module (sibling to `identity_resolver.py`) that takes a `DiscoveredIdentity`-shaped input and returns a small `InferenceResult(vendor: str | None, type_guess: DeviceType | None, raw: RawSignals)` dataclass, using `mac-vendor-lookup` (PyPI, `MacLookup`/`AsyncMacLookup`) for OUI resolution gated through a curated friendly-name dict and a single-category/multi-category vendor classification dict; (3) wiring this into `_serialize_identity()` in `devices.py` so the `/api/devices/` response carries `vendor`, `type_guess`, and a `raw_signals` object for unknown identities only.

The frontend needs one new shadcn-svelte component (`popover`, not yet installed) wired into `DeviceCard.svelte`'s unknown branch (an inference line + 44×44px info-icon trigger) and a one-line change to `RegisterDialog.svelte`'s `$state` initializers (seed `name`/`type` from the identity's inference payload instead of always `''`/`undefined`). The UI-SPEC is fully locked for both — this research does not need to make UI decisions, only confirm the data the UI consumes is shaped correctly.

**Primary recommendation:** Build inference as a pure, stateless function module (mirroring `identity_resolver.py`'s `Protocol`-based style) consuming only data already present on `DiscoveredIdentity` after the schema extension — never a live DB join at request time, and never a network call to `mac-vendor-lookup`'s `update_vendors()` (ship the bundled offline OUI snapshot only, consistent with CLAUDE.md's no-telemetry/self-hosted-only constraint).

### Pattern 1: Stateless inference module mirroring `IdentityResolver`
**What:** `identity_inference.py` exposes a single pure function `infer(identity: DiscoveredIdentity) -> InferenceResult`, with `InferenceResult` a frozen dataclass holding `vendor: str | None`, `type_guess: DeviceType | None`, `name_guess: str | None` (= `identity.hostname` when present), and `raw: RawSignals` (mac, raw_oui, mdns_service_type, dhcp_vendor_class — all optional). No DB session parameter, no I/O beyond the in-memory `AsyncMacLookup` call — keeps it trivially unit-testable, same as `HostnameFallbackResolver.resolve()`.
**When to use:** Called once per unknown identity inside `_serialize_identity()`.
**Example:**
```python
# Source: pattern derived from backend/src/services/identity_resolver.py (existing codebase style)
from dataclasses import dataclass
from src.models.device import DeviceType

@dataclass(frozen=True)
class RawSignals:
    mac: str | None
    raw_vendor: str | None
    mdns_service_type: str | None
    dhcp_vendor_class: str | None

@dataclass(frozen=True)
class InferenceResult:
    vendor: str | None
    type_guess: DeviceType | None
    name_guess: str | None
    raw: RawSignals
```

### Pattern 2: Curated vendor catalog as a plain module-level dict (D-05's "maintainable, not hardcoded branch")
**What:** Two dicts keyed by lowercase OUI-registrant substring match (since raw OUI strings are free text like "Apple, Inc." or "Sonos, Inc."): `SINGLE_CATEGORY_VENDORS: dict[str, DeviceType]` (vendor name → the one type it always implies) and `MULTI_CATEGORY_VENDORS: set[str]` (vendor names shown but never type-inferring alone). A `FRIENDLY_NAMES: dict[str, str]` maps a normalized raw-OUI-substring key to the curated display name (e.g. `"sonos"` → `"Sonos"`). Substring/contains matching (not exact match) is required because raw OUI registrant strings vary by legal entity suffix (e.g. "Sonos, Inc." vs "SONOS Inc").
**When to use:** Both dicts live in `backend/src/data/vendor_catalog.py`, imported by `identity_inference.py`. Adding a new vendor to either bucket is a one-line dict entry — satisfies D-05's "no algorithm-shape change" requirement.
**Example:**
```python
# Source: pattern designed for this codebase, no external reference (no third-party "vendor classification" library exists for this)
FRIENDLY_NAMES: dict[str, str] = {
    "apple": "Apple",
    "samsung": "Samsung",
    "sonos": "Sonos",
    "google": "Google",
    "amazon": "Amazon",
    "roku": "Roku",
    "nest labs": "Nest",
    "microsoft": "Microsoft",
}

SINGLE_CATEGORY_VENDORS: dict[str, DeviceType] = {
    "sonos": DeviceType.IOT,
    "roku": DeviceType.TV,
    "nest labs": DeviceType.IOT,
}

MULTI_CATEGORY_VENDORS: set[str] = {"apple", "samsung", "google", "amazon", "microsoft"}

def match_friendly_name(raw_oui: str) -> str | None:
    normalized = raw_oui.lower()
    for key, friendly in FRIENDLY_NAMES.items():
        if key in normalized:
            return friendly
    return None
```

### Pattern 3: mDNS/DHCP signal-to-type mapping with D-06 precedence
**What:** A small ordered lookup from mDNS service-type substrings / DHCP vendor-class substrings to `DeviceType`, checked *before* the vendor-derived guess; if it yields a result, that result wins outright regardless of what the vendor-derived guess would have been.
**When to use:** Inside `infer()`, compute `signal_type = type_from_signal(...)` first; only fall back to `type_from_vendor(...)` when `signal_type is None`.
**Example:**
```python
# Source: pattern designed for this codebase; mDNS service-type strings are RFC 6763 standard
# (e.g. _airplay._tcp, _googlecast._tcp, _hap._tcp for HomeKit) — not vendor-specific
MDNS_SERVICE_TYPE_HINTS: dict[str, DeviceType] = {
    "_googlecast._tcp": DeviceType.TV,
    "_airplay._tcp": DeviceType.TV,
    "_hap._tcp": DeviceType.IOT,        # HomeKit accessory protocol
    "_ipp._tcp": DeviceType.OTHER,       # printers — no closer enum match
}

def type_from_signal(mdns_service_type: str | None, dhcp_vendor_class: str | None) -> DeviceType | None:
    if mdns_service_type:
        for hint, dtype in MDNS_SERVICE_TYPE_HINTS.items():
            if hint in mdns_service_type:
                return dtype
    # dhcp_vendor_class strings are highly OS/stack-specific (e.g. "dhcpcd-9.4.1:Linux")
    # and rarely identify a *device category* directly — treat as supplementary only,
    # documented as an Open Question below.
    return None
```

### Anti-Patterns to Avoid
- **Showing the raw OUI registrant string as "vendor" on the card:** D-01 explicitly forbids this — only curated friendly names ever appear in the normal inference line. The raw string is allowed *only* inside the info popover (D-07/D-08).
- **Calling `update_vendors()` at runtime or on a schedule:** This silently introduces an outbound network call from a self-hosted, no-telemetry tool (CLAUDE.md constraint). Ship the bundled snapshot that comes with the pinned `mac-vendor-lookup` version; do not wire a refresh job in this phase.
- **Treating a locally-administered (randomized) MAC as a legitimate OUI lookup target:** see Pitfall 1 below — must be checked before calling `lookup()` at all, not just handled via the `VendorNotFoundError` exception path.
- **Re-deriving inference in the frontend:** UI-SPEC and this research both assume the backend is the single source of truth; the frontend only renders `vendor`/`type_guess`/`name_guess` fields already computed server-side.

## Common Pitfalls

### Pitfall 1: Locally-administered (randomized) MACs producing nonsense vendor guesses
**What goes wrong:** Modern iOS/Android devices use MAC randomization for non-trusted networks (private Wi-Fi address feature). A randomized MAC's first octet has the U/L (universal/local) bit set, and its OUI prefix does **not** correspond to any real manufacturer — `mac-vendor-lookup`'s `lookup()` will either raise `VendorNotFoundError` (most likely, since random prefixes are usually unassigned) or, worse, by chance hit a real OUI prefix that has nothing to do with the device's actual maker. `[CITED: github.com/bauerj/mac_vendor_lookup source — sanitise()/lookup() do not perform U/L bit inspection]`
**Why it happens:** The library's `lookup()` is a pure dictionary key lookup on the first 3 octets; it has no concept of "is this prefix even a valid registered OUI vs. a randomly-generated one."
**How to avoid:** Before calling `lookup()`, check the second hex digit of the MAC's first octet for the U/L bit (`int(mac_octet, 16) & 0x02 != 0` means locally administered). If set, skip vendor lookup entirely and treat as "no vendor signal" — same code path as `VendorNotFoundError`. This check is independent of and in addition to the existing `MDNS_PLACEHOLDER_MAC` check in `identity_resolver.py` — the placeholder is `00:00:00:00:00:00` (U/L bit happens to be 0, globally-administered-looking, so it would NOT be caught by the U/L check alone and must remain its own explicit exclusion).
**Warning signs:** A device card showing a vendor guess that's obviously wrong for a known-iPhone-pattern hostname, or DISC-05's success criterion 1 ("only when a real, non-placeholder MAC is available") silently passing on devices whose MAC is real-but-randomized — review test fixtures to include at least one locally-administered MAC case (e.g. `02:00:00:00:00:01`).

### Pitfall 2: `VendorNotFoundError` and `InvalidMacError` are real exceptions, not `None` returns
**What goes wrong:** `AsyncMacLookup.lookup()` raises `VendorNotFoundError` for any OUI prefix not present in the local snapshot (common — even some legitimate, less-common consumer brands), and `InvalidMacError` for malformed MAC strings. A naive `vendor = await mac.lookup(identity.mac)` will crash the request if not wrapped. `[CITED: github.com/bauerj/mac_vendor_lookup source]`
**Why it happens:** The library is designed for CLI/script use where letting exceptions propagate is acceptable; it was not designed with "always return Optional" API ergonomics for service code.
**How to avoid:** Wrap every `lookup()` call in `try/except (VendorNotFoundError, InvalidMacError): return None` inside `identity_inference.py` — this also cleanly satisfies D-01/success-criterion-3's "no reliable signal → plain Unknown" requirement, since "lookup failed" and "lookup succeeded but didn't match curated list" both collapse to the same `vendor=None` outcome.
**Warning signs:** 500 errors on `/api/devices/` for any unknown identity whose MAC's OUI isn't in the local database — would be caught immediately by any integration test that seeds an identity with an uncommon/unassigned-looking MAC, so add that case to the test plan.

### Pitfall 3: `AsyncMacLookup` is per-instance stateful (loads vendor data lazily on first `lookup()` call)
**What goes wrong:** Each `AsyncMacLookup()` instantiation starts with an empty `prefixes` dict and calls `load_vendors()` internally on first `lookup()` — if a new instance is created per-request (e.g. inside `_serialize_identity()` for every identity in a loop), the local cache load happens redundantly (though it's an in-memory file read, not network, so the perf cost is low but non-zero per Phase load).
**Why it happens:** The library's design assumes a long-lived instance (e.g. a CLI script or a single async context), not a per-call instantiation pattern.
**How to avoid:** Instantiate a single module-level `AsyncMacLookup()` in `identity_inference.py` (or as a FastAPI dependency singleton) and reuse it across all `infer()` calls within the process lifetime — mirrors how `HostnameFallbackResolver()` is already a cheap, reusable, stateless-enough object in `discovery.py`.
**Warning signs:** Slower-than-expected `/api/devices/` response times when there are many unknown identities on a single page load — profile if this becomes visible, though for a household-scale device count (tens, not thousands) this is unlikely to matter in practice.

### Pitfall 4: DHCP vendor-class strings are OS/stack identifiers, not device-category identifiers
**What goes wrong:** Real-world `dhcp_events.vendor_class_id` values look like `"dhcpcd-9.4.1:Linux-6.1.0:x86_64:"`, `"MSFT 5.0"`, or `"android-dhcp-14"` — these identify the *DHCP client software/OS*, not the device's *physical category* (phone vs. TV vs. IoT). Treating DHCP vendor class as a strong type signal (equal weight to mDNS service type) risks confident-but-wrong guesses, e.g. `"android-dhcp-14"` tells you it's Android but not whether it's a phone, tablet, or Android TV box.
**Why it happens:** DISC-06's requirement text lists "DHCP vendor class" as a signal alongside mDNS service type, but the two signals have very different reliability characteristics for category inference specifically.
**How to avoid:** Treat DHCP vendor class as a weaker/supplementary signal than mDNS service type in the `type_from_signal()` precedence — e.g. only use it for a small set of unambiguous, well-known vendor-class strings (if any are found in practice) rather than a broad mapping table. Document this explicitly as a planner decision point rather than over-promising DHCP-vendor-class coverage; see Open Questions below.
**Warning signs:** Type guesses that look suspiciously confident for devices where only a generic OS-version DHCP string was observed — review during phase verification with real captured DHCP traffic if available.

### Pitfall 5: Schema migration must backfill existing rows safely (nullable, no default-required)
**What goes wrong:** Adding `mdns_service_type`/`dhcp_vendor_class` as `NOT NULL` columns to `discovered_identities` would break existing rows created before this migration runs (Phase 2 already shipped this table with live data possible in dev/test environments).
**Why it happens:** Forgetting that Alembic migrations against a populated table need nullable-or-defaulted new columns.
**How to avoid:** Both new columns MUST be `nullable=True` (mirrors `hostname`'s existing nullable pattern on the same table) — no backfill data migration needed, since `None` simply means "no signal observed yet for this identity," which is also the correct semantic for any identity discovered before this phase shipped.
**Warning signs:** Migration failure on any environment with existing `discovered_identities` rows if a `NOT NULL` constraint is mistakenly added.

# Source: pattern matches backend/src/models/discovered_identity.py's existing hostname column
class DiscoveredIdentity(Base):

## Open Questions

1. **How rich should the DHCP-vendor-class-to-type mapping be?**
   - What we know: DHCP vendor class strings are highly variable and mostly identify OS/client-software, not device category (Pitfall 4).
   - What's unclear: Whether any of the *actual* DHCP vendor-class strings observed by this project's already-running capture pipeline (Phase 1/2) contain useful device-category signal worth mapping, since this depends on real-world traffic this research session did not have access to inspect.
   - Recommendation: Ship Phase 02.1 with mDNS service-type as the primary signal-based type guess and DHCP vendor class limited to a small, conservative set of unambiguous matches (or omitted from `type_from_signal()` entirely if no clearly reliable mapping exists) — treat DHCP-vendor-class-based type inference as an enhancement opportunity rather than a hard requirement, since DISC-06's wording says "available signals" (plural, not all-required) and D-06 only requires mDNS/DHCP collectively to win over vendor — it does not require DHCP specifically to drive a guess.

2. **Exact `Observation`/upsert wiring for the two new signal columns.**
   - What we know: `mdns_events.service_type` and `dhcp_events.vendor_class_id` already exist in the raw ingest tables; `discovered_identities` upsert currently only takes `mac`/`hostname`.
   - What's unclear: Whether the cleanest implementation extends the shared `Observation` dataclass (adding `mdns_service_type`/`dhcp_vendor_class` fields populated only by the mDNS/DHCP capture-ingest call sites, left `None` for ARP-sourced observations) vs. a separate signal-update step that reads directly from the raw event tables at upsert time. Both achieve the same end state; the `Observation`-extension approach keeps everything flowing through the existing single `record_observation()` entry point and is recommended, but the planner should confirm against the actual call sites in `capture.py`/the mDNS and DHCP ingest routes before locking this in.
   - Recommendation: Default to extending `Observation` with two new optional fields; only the mDNS-ingest and DHCP-ingest call sites populate them (ARP-only observations pass `None` for both, which is already the correct "no signal" semantic).
