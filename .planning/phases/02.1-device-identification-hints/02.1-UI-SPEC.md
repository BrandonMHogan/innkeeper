# Phase 02.1 — UI Design Contract

> Visual and interaction contract for device identification hints (inferred vendor + type guess). Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.
> Phase 02.1 scope: the unknown-device card on `/dashboard` (add a provisional inference line) and the Register dialog (pre-fill name/type fields from the same inference). This phase introduces **zero new design tokens** — it is a pure extension of Phase 2's existing design system. See `.planning/phases/02-device-registry-discovery/02-UI-SPEC.md` for the full inherited contract (spacing, typography, color, component inventory, accessibility) — not restated here except where this phase adds new copy/states.

## Color

Inherited from Phase 2's full palette and 60/30/10 split, unchanged — see `02-UI-SPEC.md` for the canonical table. **No new colors are introduced.** This phase explicitly reuses `--color-muted` for all inferred text, and explicitly avoids reusing `--color-warning` or `--color-accent` for inference, to keep the three existing semantic signals (online/accent, unknown/warning, destructive) uncontaminated by a fourth "this is a guess" signal that doesn't need its own color — italics + copy framing carry that meaning instead.

| Role | CSS Variable | Hex | Usage in this phase |
|------|-------------|-----|----------------------|
| Muted | `--color-muted` | `#64748b` | The entire "Looks like: {vendor} · {type}" line (text + icon, if used) on unknown cards; the pre-fill helper caption text in the Register dialog |
| Foreground | `--color-fg` | `#f1f5f9` | Unchanged — pre-filled input values render as normal user-editable text once typed/focused, same as any other form input value (not specially colored) |

**Explicitly NOT used for inference (reserved-for boundaries from Phase 2 still apply):**
- `--color-warning` (amber) — stays reserved for the "Unknown" badge and unknown-card dashed border only. The inference line must never borrow this color, even though both concepts live on the same card — conflating "this device is unregistered" (warning) with "this is a guess" (muted/italic) would blur two distinct signals.
- `--color-accent` (emerald) — stays reserved for online-status dot and primary buttons only.

**Color contrast check:** `--color-muted` (`#64748b`) on `--color-surface` (`#1e293b`) = ~4.6:1 — passes WCAG AA for normal text (already verified as acceptable in Phase 2's "Last seen" usage of the same pairing; this phase's inference line uses the identical pairing, so no new contrast risk).

## Layout

### Unknown device card anatomy (updated from Phase 2)

```
┌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┐  ← dashed warning border (unchanged)
┊ [?]  Unknown Device   [Unknown]┊  ← unchanged
┊                               ┊
┊ Last seen just now            ┊  ← unchanged (Body/muted)
┊ Looks like: Apple · Phone     ┊  ← NEW — Body/muted/italic, sm gap (8px) above
┊                               ┊
┊ [Register]  [Merge with...]   ┊  ← unchanged
└╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┘
```

- The inference line sits **between** "Last seen" and the action buttons, never above the badge/name row — it is supporting detail, not a headline claim.
- When only vendor is known (no type guess): `Looks like: Apple`
- When only type is known (no vendor guess): `Looks like: a phone` (lowercase, indefinite article — reads as a guess, not a label)
- When neither is known: **the entire line is omitted** — card shows only "Last seen…" then buttons, same as a no-signal unknown device looked in Phase 2. Never render `Looks like: Unknown` — that would dignify a non-guess as a guess.
- Card height is allowed to vary by one line between unknown cards with and without an inference — the grid does not need fixed-height cards (Phase 2 never required this); no layout-shift mitigation needed.

### Register dialog layout (updated from Phase 2)

```
Dialog (centered overlay, modal — unchanged)
  Title: "Register Device"
  ─────────────────────────
  Label: Name        [Input, pre-filled if hostname guess available]
         Guessed from device signals — feel free to change   ← NEW, only if pre-filled
  Label: Owner       [Input, unchanged — never pre-filled, no signal exists for owner]
  Label: Type         [Select ▾, pre-selected if type guess available]
         Guessed from device signals — feel free to change   ← NEW, only if pre-filled
  Label: Trusted      [checkbox]   ← unchanged
  ─────────────────────────
  [Cancel]              [Register Device]   ← unchanged
```

- Both pre-fill captions use identical copy for consistency: `Guessed from device signals — feel free to change`
- If the dialog opens for an unknown device with **no** name or type guess available, both fields render exactly as they did in Phase 2 (empty, no caption) — this phase changes nothing for that case.
- Pre-filled values are **fully editable, fully clearable, plain form state** — not locked, not read-only, not a separate "suggestion chip" UI. The user can backspace the name to empty or pick a different Select option with zero friction; there is no "accept suggestion" button to click through.
- The Type `<Select>` pre-selection uses the same 8-value enum and same `Select`/`SelectTrigger`/`SelectContent`/`SelectItem` components already wired in `RegisterDialog.svelte` — only the initial `$state` value changes from `undefined` to the guessed enum value when a guess exists.

## Interaction States

Inherits Phase 2's full interaction-state contract unchanged. One new behavior to declare:

| Element | Default | On user edit |
|---|---|---|
| Pre-filled Name input | Shows guessed hostname as normal editable input value (not placeholder text — it is a real, submittable value unless changed) | Once the user types, the value is simply whatever they typed — no "reverted to guess" affordance, no diffing, no special state. The helper caption remains visible regardless of edits (it's static instructional copy, not a live "still guessed" indicator) |
| Pre-filled Type select | Shows guessed type as the selected option (not the `Select a type` placeholder) | Once the user picks a different option, it's simply selected — same non-special treatment as Name |

This keeps the mental model simple: **a pre-fill is just a starting value**, not a tracked "AI suggestion" state machine. No accept/reject UI, no "powered by inference" badge inside the dialog — the helper caption is the only signal that this value didn't come from the user, and it is satisfied by static text, not interactive controls.

## Copywriting Contract

### Unknown device card (new copy this phase)

| Element | Copy | Condition |
|---|---|---|
| Inference line — vendor + type both known | `Looks like: {Vendor} · {type}` (e.g. `Looks like: Apple · phone`) | Both signals present |
| Inference line — vendor only | `Looks like: {Vendor}` (e.g. `Looks like: Sonos`) | Only vendor signal present |
| Inference line — type only | `Looks like: a {type}` (e.g. `Looks like: a smart-home device`) | Only type signal present, no vendor |
| Inference line — neither known | *(line omitted entirely — no copy rendered)* | No usable signal |

Type label casing in the inference line is lowercase and reads as natural language (`phone`, `a computer`, `a TV/streaming device`, `a smart-home device`) — distinct from the Title Case enum labels used in the Register dialog's Type dropdown (`Phone`, `Desktop`, `TV/Streaming`, `IoT/Smart Home`). Same underlying enum value, different surface casing/phrasing appropriate to each context (sentence vs. dropdown option).

### Register dialog (new copy this phase)

| Element | Copy | Condition |
|---|---|---|
| Pre-fill helper caption (Name field) | `Guessed from device signals — feel free to change` | Rendered only when Name was pre-filled from an mDNS/DHCP hostname guess |
| Pre-fill helper caption (Type field) | `Guessed from device signals — feel free to change` | Rendered only when Type was pre-selected from an inference guess |

No other dialog copy changes — title, other field labels, buttons, error message, and success behavior are all unchanged from Phase 2's `02-UI-SPEC.md`.

### Empty / no-signal state

| Element | Copy |
|---|---|
| Card with no inference signal | No special copy — card looks identical to a Phase-2-era unknown card (no "Looks like:" line at all) |
| Dialog with no inference signal | No special copy — fields render exactly as Phase 2 specified (empty Name, unselected Type, no caption) |

This directly satisfies success criterion 3: never fabricate a guess; plain absence is the correct empty state, not a placeholder "Unknown" guess value.

### Destructive actions

None introduced by this phase. No new destructive actions exist (no way to "save" an inference as fact independent of the user's own submit action — the inference is consumed entirely as a non-binding starting value, never written to the registry on its own).

## Accessibility Contract

Inherits Phase 2's accessibility contract unchanged, plus:

- The inference line's "guess, not fact" meaning must not rely on italics alone (italics can be lost to some assistive tech rendering/zoom settings) — the copy itself (`Looks like:` prefix) carries the provisional meaning in plain text, satisfying this without relying on font-style as the only signal.
- Pre-fill helper captions are real DOM text associated visually with their field (directly below, same as Phase 2's existing "Trusted devices are informational…" helper text pattern) — no `aria-describedby` wiring required beyond what Phase 2 already does for helper text, but if Phase 2's implementation already wires `aria-describedby` for the Trusted helper, apply the same pattern here for consistency (executor's discretion, not a new accessibility requirement since Phase 2 did not mandate `aria-describedby` either).
- No new icon-only controls are introduced, so no new touch-target or `aria-label` requirements beyond Phase 2's existing 44×44px minimum (unchanged, still applies to Register/Merge buttons on the card).
- Color is never the sole signal that a value is a guess (the `Looks like:` / `Guessed from device signals` copy carries the meaning in text) — consistent with Phase 2's existing rule that the "Unknown" badge text, not just color, carries that signal.

| Item | Deferred To |
|------|------------|
