# Phase 02.1 — UI Design Contract

> Visual and interaction contract for device identification hints (inferred vendor + type guess) plus the raw-signal info popover (D-07..D-09). Generated by gsd-ui-researcher, to be verified by gsd-ui-checker.
> Phase 02.1 scope: the unknown-device card on `/dashboard` (add a provisional inference line plus an info-icon popover exposing raw signals) and the Register dialog (pre-fill name/type fields from the same inference). This phase introduces **one new component install** (shadcn-svelte `popover`) and otherwise remains a pure extension of Phase 2's existing design system — no new spacing/typography/color tokens beyond what's declared below. See `.planning/phases/02-device-registry-discovery/02-UI-SPEC.md` for the full inherited contract (spacing, typography, color, component inventory, accessibility) — not restated here except where this phase adds new copy/states.
>
> **Amendment (2026-06-19):** This version adds the info icon + popover contract closing the D-10 gap flagged in `02.1-CONTEXT.md`. Everything else in this document — the inference line layout/copy, the Register dialog pre-fill treatment, spacing/typography/color for those elements — is unchanged from the prior approved version and is carried forward as-is.

## Color

Inherited from Phase 2's full palette and 60/30/10 split, unchanged — see `02-UI-SPEC.md` for the canonical table. **No new colors are introduced.** This phase explicitly reuses `--color-muted` for all inferred text, and explicitly avoids reusing `--color-warning` or `--color-accent` for inference, to keep the three existing semantic signals (online/accent, unknown/warning, destructive) uncontaminated by a fourth "this is a guess" signal that doesn't need its own color — italics + copy framing carry that meaning instead.

| Role | CSS Variable | Hex | Usage in this phase |
|------|-------------|-----|----------------------|
| Muted | `--color-muted` | `#64748b` | The entire "Looks like: {vendor} · {type}" line (text + icon, if used) on unknown cards; the pre-fill helper caption text in the Register dialog |
| Foreground | `--color-fg` | `#f1f5f9` | Unchanged — pre-filled input values render as normal user-editable text once typed/focused, same as any other form input value (not specially colored) |

**Explicitly NOT used for inference (reserved-for boundaries from Phase 2 still apply):**
- `--color-warning` (amber) — stays reserved for the "Unknown" badge and unknown-card dashed border only. The inference line must never borrow this color, even though both concepts live on the same card — conflating "this device is unregistered" (warning) with "this is a guess" (muted/italic) would blur two distinct signals.
- `--color-accent` (emerald) — stays reserved for online-status dot and primary buttons only.

**Color contrast check:** `--color-muted` (`#64748b`) on `--color-surface` (`#1e293b`) = ~4.6:1 — passes WCAG AA for normal text (already verified as acceptable in Phase 2's "Last seen" usage of the same pairing; this phase's inference line uses the identical pairing, so no new contrast risk).

### Info icon + popover color (amendment)

| Element | State | CSS Variable | Hex | Usage |
|---|---|---|---|---|
| Info icon (glyph) | Resting | `--color-muted` | `#64748b` | Matches the inference line's own color — the icon is a quiet extension of the line it sits next to, not a call-to-action |
| Info icon (glyph) | Hover / focus-visible | `--color-fg` | `#f1f5f9` | Brightens on hover/focus to confirm it is interactive, consistent with Phase 2's existing icon-affordance pattern (device-type icons stay static; this is a new *interactive* icon, so it needs its own hover signal — `--color-fg` is the same brightening Phase 2 already uses for card border hover, applied here to the icon itself) |

| Popover surface | — | `--color-surface` | `#1e293b` | Same secondary surface as cards/dialogs — popover never introduces a third surface tone |
| Popover border | — | `--color-border` | `#334155` | Matches existing card/input border |
| Popover label text | — | `--color-muted` | `#64748b` | Field labels ("MAC", "Vendor (raw)", etc.) — de-emphasized relative to the value |

**Explicitly NOT used for the info icon or popover:**
- `--color-warning` — the icon is a neutral disclosure affordance, not a warning signal; using warning-amber here would wrongly suggest the raw data itself is a problem.
- `--color-accent` — reserved for online-status dot and primary buttons only (unchanged reserved-for boundary from Phase 2 and from this document's own Color section above).

**Color contrast check (amendment):**
- Info icon resting: `--color-muted` (`#64748b`) on `--color-surface` (`#1e293b`) ≈ 4.6:1 — passes WCAG AA (non-text/icon UI components require 3:1 per WCAG 1.4.11; this exceeds it, and also passes the stricter 4.5:1 text threshold as a margin of safety since the icon sits adjacent to text).
- Info icon hover/focus/open: `--color-fg` (`#f1f5f9`) on `--color-surface` (`#1e293b`) ≈ 14.9:1 — passes WCAG AAA.
- Popover value text (mono): `--color-fg` (`#f1f5f9`) on `--color-surface` (`#1e293b`) ≈ 14.9:1 — passes WCAG AAA.
- Popover label text: `--color-muted` (`#64748b`) on `--color-surface` (`#1e293b`) ≈ 4.6:1 — passes WCAG AA for normal text (identical pairing already verified above for the inference line).

## Layout

### Unknown device card anatomy (updated from Phase 2)

```
┌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┐  ← dashed warning border (unchanged)
┊ [?]  Unknown Device   [Unknown]┊  ← unchanged
┊                               ┊
┊ Last seen just now            ┊  ← unchanged (Body/muted)
┊ Looks like: Apple · Phone (i) ┊  ← NEW — Body/muted/italic line + info icon, sm gap (8px) above
┊                               ┊
┊ [Register]  [Merge with...]   ┊  ← unchanged
└╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┘
```

- The inference line sits **between** "Last seen" and the action buttons, never above the badge/name row — it is supporting detail, not a headline claim.
- When only vendor is known (no type guess): `Looks like: Apple`
- When only type is known (no vendor guess): `Looks like: a phone` (lowercase, indefinite article — reads as a guess, not a label)
- When neither is known: **the entire line is omitted, including the info icon** — card shows only "Last seen…" then buttons, same as a no-signal unknown device looked in Phase 2. Never render `Looks like: Unknown` — that would dignify a non-guess as a guess. (The popover would have nothing useful to show either, since at minimum the MAC is the only guaranteed raw field — see Copywriting amendment below for the case where the MAC itself is the placeholder.)
- Card height is allowed to vary by one line between unknown cards with and without an inference — the grid does not need fixed-height cards (Phase 2 never required this); no layout-shift mitigation needed.

### Info icon + popover layout (amendment)

```
Looks like: Apple · Phone (i)  ← info icon, 4px gap after text, inline, 44×44px hit area
                 │
                 ▼ (click/tap toggles open — same trigger toggles closed)
        ┌─────────────────────────────┐
        │ MAC          aa:bb:cc:11:22:33│  ← Label (14px/500/muted) + value (14px/400 mono/fg)
        │ Vendor (raw) Hon Hai Precision │
        │              Industry Co.,Ltd. │
        │ mDNS         _airplay._tcp     │  ← only present if observed
        │ DHCP class   dhcpcd-9.4.1:Linux│  ← only present if observed
        └─────────────────────────────┘
```

- Popover opens anchored to the info icon trigger; horizontal/vertical placement and collision avoidance (flipping above the card near a viewport edge, etc.) is handled automatically by the Bits UI `Popover` primitive's default floating-UI behavior — no custom positioning logic needed.
- Internal layout: a simple label/value list, one row per present signal, `sm` (8px) vertical gap between rows, `md` (16px) padding around the popover content (matches Phase 2's existing dialog/card padding scale).
- Labels and values sit side-by-side on wide popovers or stack on narrow/mobile viewports — either is acceptable; the contract only requires each label be visually associated with its value (proximity + the Label/mono-Body type contrast is sufficient, no specific breakpoint behavior is mandated).
- Popover width: content-sized up to a max of ~280px, wrapping long values (e.g. a long raw OUI registrant string) rather than truncating — D-08 requires the *raw* string be shown in full, so truncation with ellipsis is not acceptable here (unlike elsewhere in the app where truncation may be fine).
- Rows for signals that were not observed are omitted entirely (no "mDNS: —" or "mDNS: not observed" row) — consistent with D-08's "each shown only if present" instruction, and consistent with this document's existing "omit, don't fabricate" pattern used for the inference line itself.

### Register dialog layout (updated from Phase 2)

```
Dialog (centered overlay, modal — unchanged)
  Title: "Register Device"
  ─────────────────────────
  Label: Name        [Input, pre-filled if hostname guess available]
         Guessed from device signals — feel free to change   ← NEW, only if pre-filled
  Label: Owner       [Input, unchanged — never pre-filled, no signal exists for owner]
  Label: Type         [Select ▾, pre-selected if type guess available]
         Guessed from device signals — feel free to change   ← NEW, only if pre-filled
  Label: Trusted      [checkbox]   ← unchanged
  ─────────────────────────
  [Cancel]              [Register Device]   ← unchanged
```

- Both pre-fill captions use identical copy for consistency: `Guessed from device signals — feel free to change`
- If the dialog opens for an unknown device with **no** name or type guess available, both fields render exactly as they did in Phase 2 (empty, no caption) — this phase changes nothing for that case.
- Pre-filled values are **fully editable, fully clearable, plain form state** — not locked, not read-only, not a separate "suggestion chip" UI. The user can backspace the name to empty or pick a different Select option with zero friction; there is no "accept suggestion" button to click through.
- The Type `<Select>` pre-selection uses the same 8-value enum and same `Select`/`SelectTrigger`/`SelectContent`/`SelectItem` components already wired in `RegisterDialog.svelte` — only the initial `$state` value changes from `undefined` to the guessed enum value when a guess exists.

## Interaction States

Inherits Phase 2's full interaction-state contract unchanged. One new behavior to declare:

| Element | Default | On user edit |
|---|---|---|
| Pre-filled Name input | Shows guessed hostname as normal editable input value (not placeholder text — it is a real, submittable value unless changed) | Once the user types, the value is simply whatever they typed — no "reverted to guess" affordance, no diffing, no special state. The helper caption remains visible regardless of edits (it's static instructional copy, not a live "still guessed" indicator) |
| Pre-filled Type select | Shows guessed type as the selected option (not the `Select a type` placeholder) | Once the user picks a different option, it's simply selected — same non-special treatment as Name |

This keeps the mental model simple: **a pre-fill is just a starting value**, not a tracked "AI suggestion" state machine. No accept/reject UI, no "powered by inference" badge inside the dialog — the helper caption is the only signal that this value didn't come from the user, and it is satisfied by static text, not interactive controls.

### Info icon + popover interaction (amendment)

| Trigger / state | Behavior |
|---|---|
| Click/tap on info icon (popover closed) | Popover opens. Identical behavior on mouse and touch input — this is a click/tap-to-toggle pattern per D-09, never a hover-only tooltip. |
| Click/tap on info icon (popover open) | Popover closes (toggle) — clicking the trigger again is the primary way to close it. |
| Click/tap anywhere outside the popover content (popover open) | Popover closes (click-away-to-dismiss). This is the Bits UI `Popover` primitive's default behavior — no custom outside-click handler needs to be written. |
| `Escape` key (popover open, any input method) | Popover closes. Also a Bits UI default. |
| Hover over info icon (no click) | **No popover opens on hover alone** — hover only triggers the resting→hover color change on the icon glyph itself (see Color amendment). This is the explicit distinction from a tooltip pattern: hover gives a visual hint that the icon is interactive, but never reveals the popover content without an explicit click/tap, keeping desktop and touch behavior identical per D-09. |
| Focus via keyboard (Tab to icon) + `Enter`/`Space` | Popover opens, same as click — the trigger is a real `<button>`, so native keyboard activation works without extra wiring. |
| Multiple unknown cards on the dashboard | Only one popover may reasonably be open at a time in practice (clicking a different card's info icon should open that popover; whether the previous one auto-closes or simply becomes visually distant is acceptable either way — Bits UI's default per-instance behavior is sufficient, no explicit "only one popover globally" state management is required as a contract item) |

This is the one interaction-state addition this phase introduces beyond Phase 2's existing contract; everything else in this section (pre-fill input/select behavior) is unchanged from the original approved version.

## Copywriting Contract

### Unknown device card (new copy this phase)

| Element | Copy | Condition |
|---|---|---|
| Inference line — vendor + type both known | `Looks like: {Vendor} · {type}` (e.g. `Looks like: Apple · phone`) | Both signals present |
| Inference line — vendor only | `Looks like: {Vendor}` (e.g. `Looks like: Sonos`) | Only vendor signal present |
| Inference line — type only | `Looks like: a {type}` (e.g. `Looks like: a smart-home device`) | Only type signal present, no vendor |
| Inference line — neither known | *(line omitted entirely — no copy rendered)* | No usable signal |

Type label casing in the inference line is lowercase and reads as natural language (`phone`, `a computer`, `a TV/streaming device`, `a smart-home device`) — distinct from the Title Case enum labels used in the Register dialog's Type dropdown (`Phone`, `Desktop`, `TV/Streaming`, `IoT/Smart Home`). Same underlying enum value, different surface casing/phrasing appropriate to each context (sentence vs. dropdown option).

### Register dialog (new copy this phase)

| Element | Copy | Condition |
|---|---|---|
| Pre-fill helper caption (Name field) | `Guessed from device signals — feel free to change` | Rendered only when Name was pre-filled from an mDNS/DHCP hostname guess |
| Pre-fill helper caption (Type field) | `Guessed from device signals — feel free to change` | Rendered only when Type was pre-selected from an inference guess |

No other dialog copy changes — title, other field labels, buttons, error message, and success behavior are all unchanged from Phase 2's `02-UI-SPEC.md`.

### Empty / no-signal state

| Element | Copy |
|---|---|
| Card with no inference signal | No special copy — card looks identical to a Phase-2-era unknown card (no "Looks like:" line at all) |
| Dialog with no inference signal | No special copy — fields render exactly as Phase 2 specified (empty Name, unselected Type, no caption) |

This directly satisfies success criterion 3: never fabricate a guess; plain absence is the correct empty state, not a placeholder "Unknown" guess value.

### Raw-signal info popover (amendment — new copy this phase)

Per D-08, popover content is **raw signals only** — no narrative/reasoning text explaining which signal "won" or why a guess was made. Each row is a plain label + the literal value, full stop.

| Row | Label copy | Value | Condition |
|---|---|---|---|
| MAC address | `MAC` | The device's literal MAC address (e.g. `aa:bb:cc:11:22:33`), monospace | Always shown if the identity has a non-placeholder MAC. **Never shown** (row omitted) when the only MAC on record is the `MDNS_PLACEHOLDER_MAC` sentinel (`00:00:00:00:00:00`) — showing the placeholder as if it were a real MAC would itself be a fabrication, inconsistent with this phase's "never dignify a non-signal" principle applied throughout the rest of this document |
| Raw OUI vendor string | `Vendor (raw)` | The full, uncurated OUI registrant string exactly as returned by the underlying lookup (e.g. `Hon Hai Precision Industry Co.,Ltd.`) — deliberately the *uncleaned* counterpart to D-01's curated friendly name, monospace, wrapped not truncated | Shown only if a non-placeholder MAC resolved to *any* OUI registrant string, even one that didn't match the curated shortlist (i.e., this row may appear even when the card's "Looks like:" line shows no vendor at all — that is the entire point of the transparency feature) |
| mDNS service type | `mDNS` | The raw service type string as observed (e.g. `_airplay._tcp`, `_googlecast._tcp`), monospace | Shown only if an mDNS service type was actually observed for this identity |
| DHCP vendor class | `DHCP class` | The raw DHCP vendor class string as observed (e.g. `dhcpcd-9.4.1:Linux-6.1.0:x86_64:`), monospace, wrapped not truncated | Shown only if a DHCP vendor class was actually observed for this identity |
| No signals present at all | *(popover content is a single line, no rows)* | `No raw signal data available.` | Edge case: an unknown identity that somehow has an inference-line guess from a source not covered above, or whose only signal was the placeholder MAC. Keeps the popover from ever rendering visually empty/broken — this is the only piece of popover copy that isn't a literal raw value, and it states absence plainly rather than fabricating content, consistent with D-08's "facts only" rule |

No row ever includes phrasing like "this suggested the guess because…" or "primary signal" — that would be reasoning/narrative text, which D-08 explicitly excludes. The row labels are nouns naming the signal, not sentences explaining its role in the inference.

### Destructive actions

None introduced by this phase. No new destructive actions exist (no way to "save" an inference as fact independent of the user's own submit action — the inference is consumed entirely as a non-binding starting value, never written to the registry on its own). The info popover is read-only and non-destructive — opening/closing it has no side effects.

## Accessibility Contract

Inherits Phase 2's accessibility contract unchanged, plus:

- The inference line's "guess, not fact" meaning must not rely on italics alone (italics can be lost to some assistive tech rendering/zoom settings) — the copy itself (`Looks like:` prefix) carries the provisional meaning in plain text, satisfying this without relying on font-style as the only signal.
- Pre-fill helper captions are real DOM text associated visually with their field (directly below, same as Phase 2's existing "Trusted devices are informational…" helper text pattern) — no `aria-describedby` wiring required beyond what Phase 2 already does for helper text, but if Phase 2's implementation already wires `aria-describedby` for the Trusted helper, apply the same pattern here for consistency (executor's discretion, not a new accessibility requirement since Phase 2 did not mandate `aria-describedby` either).
- Color is never the sole signal that a value is a guess (the `Looks like:` / `Guessed from device signals` copy carries the meaning in text) — consistent with Phase 2's existing rule that the "Unknown" badge text, not just color, carries that signal.

### Info icon + popover accessibility (amendment — supersedes the prior "no new icon-only controls" statement)

**Correction to the original contract:** the previous version of this document stated "No new icon-only controls are introduced." That is no longer accurate — the info icon (D-07) is a new icon-only interactive control. The requirements below apply to it specifically and extend, rather than contradict, Phase 2's existing icon-only-control rules (which still govern the unchanged Register/Merge buttons).

- **Touch target:** the info icon trigger MUST have a minimum **44×44px** hit area, per Phase 2's existing icon-only touch-target precedent (`02-UI-SPEC.md` line 63, line 330) extended to this new control — see Spacing amendment above for implementation detail (padding on the trigger, not the glyph).
- **`aria-label`:** the trigger button MUST carry `aria-label="Show raw signal data"` (or equivalent wording communicating the same intent) since it has no visible text label — only the `Info` glyph. This is required, not optional, because the icon alone conveys no accessible name to screen reader users.
- **Keyboard operability:** the trigger is a real `<button>` element (not a `<div>` with a click handler), so it is natively focusable and activatable via `Enter`/`Space` without any custom `tabindex`/`keydown` wiring. This is a hard requirement, not an implementation suggestion — D-09's "must work identically on desktop and touch" extends to keyboard-only use as a third input modality the contract implicitly covers.
- **Focus visibility:** the trigger shows a visible focus ring on keyboard focus, consistent with Phase 2's existing focus-ring pattern already applied to the Register/Merge buttons (`02-UI-SPEC.md`'s Interaction States table) — same focus treatment, new element.
- **Popover content accessibility:** the popover's label/value rows are plain text content, read top-to-bottom by assistive tech in DOM order — no `aria-live` announcement is needed (opening the popover is a deliberate user action, not an unsolicited update), but the popover content container should be associated with the trigger via the Bits UI `Popover` primitive's built-in ARIA wiring (`aria-expanded`, `aria-controls`/`aria-describedby` equivalent) — this is the primitive's default behavior, not something the executor needs to hand-roll.
- **Dismissal:** `Escape` closes the popover and returns focus to the trigger button — this is the Bits UI `Popover` primitive's default focus-management behavior, satisfying the expectation that closing an overlay never strands keyboard focus on a removed element.
- **Contrast:** see the Color amendment's contrast-check subsection above — all popover text/icon color pairings pass WCAG AA at minimum (most pass AAA).
