<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser → API (`/api/devices/*`) | User-supplied form input (name/owner/type/trusted, merge target selection) crosses here — relies entirely on Plan 01's backend validation (Pydantic `DeviceType` enum, `require_auth`); the frontend has no independent trust boundary of its own |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-02-10 | Tampering | Register/Merge dialog form fields (XSS via device name rendered elsewhere) | mitigate | Svelte's default text interpolation (`{expression}`) auto-escapes; no `{@html}` used anywhere in DeviceCard/dialogs for user-supplied strings (name, owner, hostname) |
| T-02-11 | Information Disclosure | Device list response includes hostname/MAC-derived data in the unknown-card payload | accept | Already behind `require_auth` session gate (Plan 01); same-LAN single-user tool, no additional frontend-side mitigation needed |
| T-02-12 | Tampering | Type dropdown bypass (client sends arbitrary `type` string directly to API, bypassing the `Select`'s fixed option list) | mitigate | Defense-in-depth already exists server-side: `DeviceRegisterPayload.type: DeviceType` (Plan 01) rejects non-enum values regardless of what the client sends — frontend `Select` constraining the UI is a UX nicety, not the actual security boundary |
</threat_model>
