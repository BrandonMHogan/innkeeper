# Phase 2 — UI Design Contract

> Visual and interaction contract for the device registry + discovery phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Phase 2 scope: `/dashboard` device card grid, summary banner, Register form (Dialog), Merge picker (Dialog). Builds on Phase 1's auth shell and dark theme — does not redefine it.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn-svelte (now initialized — see note) |
| Preset | `mist` base color (closest available match to Phase 1's slate-based dark palette; stable `shadcn-svelte.com` registry, not the retired `@next` line) |

**shadcn-svelte initialization note (read before extending this contract):**

`components.json` did not exist at the start of Phase 2 — Phase 1 used Bits UI directly without the CLI scaffold. It is now initialized:

- `components.json` created (base color `mist`, CSS file `src/lib/styles/theme.css`, aliases `$lib/components`, `$lib/components/ui`, `$lib/utils`, `$lib/hooks`).
- The `shadcn-svelte@next` CLI line is **retired** — `next.shadcn-svelte.com` 302-redirects to `shadcn-svelte.com`. Always use `shadcn-svelte@latest` (currently `1.3.0`) going forward, never `@next`.
- The current stable CLI's `init` command requires an interactive preset selection (or a `--preset {string}` generated at `shadcn-svelte.com/create`) that could not be driven non-interactively in this environment. `components.json` and the token CSS were therefore authored directly (schema-verified against the live registry, content-verified by `npm run build` + `svelte-check` passing clean) rather than run through the init wizard. Functionally equivalent — `npx shadcn-svelte add {component}` works correctly against this config (verified by installing `card`, `button`, `badge`, `dialog`, `select`, `separator`, `label`, `input`).
- Components installed for Phase 2: `card`, `button`, `badge`, `dialog`, `select`, `separator`, `label`, `input` — all under `src/lib/components/ui/`.
- `src/lib/utils.ts` created with the standard `cn()` helper (`clsx` + `tailwind-merge`) and `WithElementRef`/`WithoutChild` types — required by every shadcn-svelte component, did not exist before.
- `tw-animate-css`, `clsx`, `tailwind-merge`, `tailwind-variants` added as dependencies (required by the installed components).
- `<html class="dark">` is now set in `src/app.html` so shadcn-svelte's `dark:` variants resolve. Innkeeper is dark-only (Phase 1 decision); this does not introduce a light/dark toggle.

**Theme token architecture — two layers, kept in sync intentionally:**

1. **Phase 1 brand aliases** (`--color-background`, `--color-surface`, `--color-border`, `--color-accent`, `--color-fg`, `--color-muted`, `--color-destructive`, `--color-accent-button-bg`) — unchanged hex values, still used by existing inline-styled Phase 1 markup (`/setup`, `/login`, dashboard shell). Do not remove.
2. **Standard shadcn-svelte tokens** (`--background`, `--foreground`, `--card`, `--primary`, `--secondary`, `--muted`, `--accent`, `--destructive`, `--border`, `--input`, `--ring`, plus new **`--warning`**) — required by every installed component's Tailwind classes (`bg-card`, `bg-primary`, `text-muted-foreground`, etc.). Mapped via CSS variable indirection to the *same* hex values as layer 1, so there is exactly one palette expressed twice. Declared in `.dark` (since `<html>` always carries the `dark` class) and exposed to Tailwind v4 via `@theme inline`.

Swapping the entire theme means editing hex values in `:root`/`.dark` in `src/lib/styles/theme.css` only — no component file ever hardcodes a color.

## Color

Dark theme, inherited base from Phase 1 (60/30/10 unchanged), **plus one new semantic color for Phase 2: warning (amber)**.

| Role | CSS Variable | Hex | Tailwind equivalent | Usage |
|------|-------------|-----|---------------------|-------|
| Dominant (60%) | `--color-background` | `#0f172a` | slate-900 | Page background |
| Secondary (30%) | `--color-surface` | `#1e293b` | slate-800 | Device cards, summary banner, dialog surface |
| Surface border | `--color-border` | `#334155` | slate-700 | Card outlines, input borders, dividers |
| Accent (10%) | `--color-accent` | `#10b981` | emerald-500 | Accent reserved-for list below |
| Foreground | `--color-fg` | `#f1f5f9` | slate-100 | Primary text, headings |
| Muted | `--color-muted` | `#64748b` | slate-500 | Last-seen timestamps, placeholder text, helper copy |
| Destructive | `--color-destructive` | `#ef4444` | red-500 | Destructive actions only |
| **Warning (new)** | `--color-warning` | `#f59e0b` | amber-500 | Unknown-device badge/border only — see below |
| Warning foreground | `--color-warning-fg` | `#1f2937` | slate-800 | Text on warning-colored badge fill |

**Accent (`#10b981`, emerald-500) is reserved exclusively for:**
- The **online status dot** on registered device cards (small filled circle, 8px diameter)
- The primary submit button fill on Register/Merge dialogs (inherited from Phase 1's submit-button pattern — uses `#059669` emerald-600 for AA contrast, same override as Phase 1)
- Active/focused state ring on interactive elements (`ring-emerald-500/50`, inherited from Phase 1)

**Warning (`#f59e0b`, amber-500) is reserved exclusively for:**
- The "Unknown" badge on unregistered device cards
- The dashed border treatment on unregistered device cards
- The unknown-device count in the summary banner (e.g. the "2" in "2 unknown" — text colored, not background)

Warning is **distinct from destructive red** and **distinct from accent green** — these are three separate semantic signals (success/online, caution/unknown, danger/destructive-action) and must never be conflated. Offline devices use **muted gray** (not red, not warning) — offline is a neutral state, not an error.

**Accent and warning are NOT used for:**
- General interactive hover/focus states outside the reserved list above
- Icons inside device cards (device-type icons use `--color-fg` or `--color-muted`, never accent/warning — color is reserved for status signaling only)
- Borders on registered (known) device cards — only unknown cards get a colored border

**Status dot color map (registered device cards):**

| Device state | Dot color | Notes |
|---|---|---|
| Online | `--color-accent` (emerald-500) | Filled circle, 8px |
| Offline | `--color-muted` (slate-500) | Filled circle, 8px, no glow/ring |

Unknown (unregistered) devices do not get a status dot — they get the "Unknown" badge instead (badge replaces dot for that card type).

## Layout

### Device card grid breakpoints

| Viewport width | Columns | Notes |
|---|---|---|
| < 640px | 1 | Mobile — full-width cards |
| 640px – 1024px | 2 | Tablet |
| 1024px – 1440px | 3 | Standard desktop |
| > 1440px | 4 | Wide desktop |

- **Minimum card width:** 280px (grid uses `grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))` or explicit breakpoint columns — either implementation satisfies the contract as long as min-width and column counts at each range hold)
- **Grid gap:** `lg` token (24px), both row and column gap
- Unknown (unregistered) device cards are **sorted to the top** of the grid, before any registered device cards (D-10) — grid order, not a separate section

## Accessibility Contract

- All dialog forms have `<label>` elements with explicit `for`/`id` binding (inherited from Phase 1's pattern) — no `aria-label` substitutes on visible inputs
- `Dialog` traps focus while open (Bits UI default behavior) and returns focus to the triggering button on close
- Status dots are decorative color signals only — the underlying online/offline state must also be conveyed in text (e.g. card has a visually-hidden `sr-only` "Online" / "Offline" label, or the last-seen text itself implies state) so color-blind users and screen readers aren't dependent on dot color alone
- The "Unknown" badge text itself (not just the warning color/dashed border) is the primary signal for unregistered devices — never color-only
- Icon-only inline buttons get `aria-label` (none expected in Phase 2 — both "Register" and "Merge with..." have visible text labels)
- Minimum touch target: 44×44px for all card action buttons, consistent with Phase 1
- Color contrast: `--color-warning` (`#f59e0b`) on `--color-surface` (`#1e293b`) = ~7.6:1 (WCAG AA/AAA for text); warning badge uses `--color-warning-fg` (`#1f2937`) on `--color-warning` fill = ~8.4:1
- Tab order on device card (unknown): Register button → Merge with... button (in DOM order, left to right)
- Tab order in Register dialog: Name → Owner → Type → Trusted checkbox → Cancel → Register Device
- Tab order in Merge dialog: Merge-into select → Cancel → Merge Devices
